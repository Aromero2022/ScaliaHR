# Scalia HR — Architecture Decisions

> SaaS B2B HCM multi-tenant, modular clone of SAP SuccessFactors.
> Stack: Next.js 15 (App Router) + Supabase + Prisma (client-only).

---

## D1 — Single Source of Schema

**Decision:** `supabase/migrations/` (raw SQL) is the **only** source of truth
for the database schema. Prisma is used exclusively as a type-generation client
via `npm run db:sync` (`prisma db pull && prisma generate`).

**Rationale:** Supabase RLS policies, custom functions (`requesting_tenant_id`,
`is_tenant_admin`, `custom_access_token_hook`), FORCE ROW LEVEL SECURITY, enum
types, and GRANTs cannot be expressed in Prisma's migration DSL. Maintaining two
migration chains (Prisma + SQL) creates drift and security gaps.

**Rules:**
- `prisma migrate` and `prisma db push` are **prohibited**.
- `prisma/migrations/` directory must not exist.
- `schema.prisma` uses `@@map`/`@map` only as generated by `db pull`.
- Every business table has `tenant_id uuid NOT NULL` with a FK to `tenants(id)`.

## D2 — Tenant in the JWT

**Decision:** The active tenant is injected into the Supabase JWT via a
`custom_access_token_hook`. RLS policies read it with
`public.requesting_tenant_id()` (JWT-only, no fallback).

> **S1 change:** `current_tenant_id()` was dropped. All callers now use
> `requesting_tenant_id()`, which reads **only** the JWT claim — no
> `set_config` fallback.

**Tables:**
- `user_tenant_memberships` — maps users to tenants with `app_role` and
  `is_active` flag. Composite PK `(user_id, tenant_id)`.
- `user_settings` — stores `active_tenant_id` per user.

**Hook:** `public.custom_access_token_hook(event jsonb)` (SECURITY DEFINER,
`search_path = ''`) adds `tenant_id` and `app_role` claims from the active
membership. Only `supabase_auth_admin` can execute it.

**Client:**
- `switchTenant(tenantId)` Server Action validates membership (Zod + DB),
  updates `active_tenant_id`, refreshes session.
- `revokeMembership` deactivates the membership and signs out the user globally.

## D3 — Prisma Without RLS Bypass

**Decision:** The Prisma connection uses a custom PostgreSQL role `prisma_app`
with `NOBYPASSRLS`. Every query runs inside a `$transaction` that first sets
`role authenticated` and injects JWT claims via `set_config`.

**Implementation:**
- `lib/db/tenant-client.ts` — sets `request.jwt.claims` per operation.
- `lib/db/admin-client.ts` — privileged connection, importable only from
  `lib/jobs/` and `lib/admin/`.
- ESLint `no-restricted-imports` enforces boundaries.

**Connection URL:** `DATABASE_URL` connects through the Supabase pooler as
`prisma_app.<project-ref>` on port 6543 (transaction mode). The password is
set by the `db-remote-sync` workflow from the `PRISMA_APP_PASSWORD` secret in
the `remote-db` GitHub environment. See `.env.example` for the full URL format.

## D4 — Secrets & Network Hardening

**Rules:**
- All secrets read from `.env` (never committed). `.env.example` has
  placeholders only.
- Docker services publish ports on `127.0.0.1` only.
- `check:forbidden` (`scripts/check-forbidden.sh`, run as `npm run
  check:forbidden`) enforces two categories:
  1. **Old project name** — the pattern is assembled at runtime from string
     fragments so the script never contains the literal name. It searches
     ALL git-tracked file contents and filenames with zero exceptions.
  2. **Secret patterns** — `"service_role"`, `"bitnami"`, `"MOODLE_WS_TOKEN"`
     in client code (`apps/web/src`, `packages`); server-only files that
     legitimately reference them are allowlisted inside the script.
- The check runs in three places: CI (`app` job, before lint), pre-commit
  (husky + lint-staged on `*.{ts,tsx,js,jsx,json,yml,yaml,md,sql,sh,toml}`),
  and a Vitest test (`forbidden-name.test.ts`).

## D5 — LMS Integration (Moodle)

**Decision:** Moodle (`moodlehq/moodle-php-apache`) runs as a sidecar service
alongside the application stack. Scalia HR communicates with it exclusively via
REST web services, using a single service token (`MOODLE_WS_TOKEN`) stored
server-side.

**SSO:** `auth_userkey` plugin, mapping by `username` = Supabase user UUID.
The `/lms/launch` route auto-provisions the Moodle user on first access and
redirects via `auth_userkey_request_login_url`.

**Tenant Isolation:**
- Each tenant gets its own Moodle **category** (courses) and **cohort**
  (employees), stored in `lms_tenant_map`.
- `lms_user_map` associates each Supabase user with their Moodle user ID.
- Both tables have RLS ENABLED + FORCED, scoped by JWT `tenant_id`.

**Sync (`lib/jobs/lms-sync.ts`):**
- ACTIVE + unmapped → create Moodle user, add to cohort, store mapping.
- TERMINATED + mapped → suspend in Moodle.
- `is_anonymized` + mapped → suspend + anonymize (ARCO: firstname=Usuario,
  lastname=Anonimizado, email=`anon_{id}@scalia.local`).
- ACTIVE + mapped → unsuspend (rehire).

**Security:**
- `moodle-client.ts` starts with `import "server-only"` (D30; it replaced a
  `typeof window` check), so a client import fails the build.
- `MOODLE_WS_TOKEN` is in the `check:forbidden` list.
- Server-only files (moodle-client, provision-tenant, lms-sync) are allowlisted.
- Moodle Docker service binds only to `127.0.0.1`.

## D6 — S1 Security Hardening

**Decision:** Harden all SECURITY DEFINER functions, unify tenant resolution,
add RESTRICTIVE RLS policies on PII/compensation tables, rewrite ARCO policies
to role-based access, and consolidate RBP to v2 model.

**Changes (Loop S1):**

1. **`requesting_tenant_id()`** — now the ONLY tenant function. Reads JWT claim
   only, no `set_config` fallback. `current_tenant_id()` dropped.

2. **SECURITY DEFINER functions** — all now have `SET search_path = ''` with
   fully schema-qualified references: `is_tenant_admin`, `insert_effective_record`,
   `effective_record_at`, `anonymize_user`, `export_user_data`.

3. **ARCO policies** — rewritten with `requesting_tenant_id()` + role-based
   access: subject sees own requests (SELECT), admin manages (INSERT/UPDATE).
   `service_role` bypass added.

4. **PII RESTRICTIVE policies** — `ec_personal_information` and `ec_compensation`
   now have RESTRICTIVE SELECT policies: user sees own + direct manager +
   tenant admin. INSERT/UPDATE restricted to admin only.
   Helper functions: `current_app_user_id()`, `has_app_role(text)`.

5. **RBP v2 model** — `can()` and Admin Center UI rewritten to use v2 tables:
   - `role_grants` (with `target_population` enum) replaces `role_assignments`
   - `group_members` replaces `permission_groups.criteria_json` for membership
   - `role_permissions.permission_key/action/field_key` replaces `permission_name`
   - v1 artefacts dropped (`role_assignments` table, `criteria_json` column, `permission_name` column)

6. **CI** — Prisma drift check added to db job. Integration tests moved to
   `__tests__/integration/`. New S1 integration tests (17 cases).
   `mfa-flow.test.ts` verifies TOTP enroll/verify against the local
   Supabase auth server (AAL1→AAL2 promotion, policy guards, invalid code
   rejection). `module-flags.test.ts` verifies flag gating and RLS
   isolation between tenants.

## D7 — Migration Policy & Remote Sync

**Decision:** Changes to the remote Supabase database are applied **only** through
the `db-remote-sync` GitHub Actions workflow, never manually or via the Supabase
MCP `apply_migration` / `execute_sql` tools.

**Workflow:** `.github/workflows/db-remote-sync.yml`
- **Trigger:** `workflow_dispatch` only (manual from GitHub Actions UI).
- **Environment:** `remote-db` (requires approval + secrets).
- **Secrets:** `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_URL`, `SUPABASE_PROJECT_REF`.
- **Modes:**
  - `production` — applies pending migrations only, never touching the history
    (D22). The only mode allowed for target `production`.
  - `reset` — pushes all local migrations from scratch (`supabase db push --include-all`).
  - `repair-push` — reverts remote-only migrations, then pushes.
- **Safety:** requires typing `CONFIRM`, creates a schema + data backup uploaded as
  an artifact (retained 30 days), and verifies with `supabase db diff --linked`
  after applying.

**Rules:**
- `supabase/migrations/` on `main` with CI green is the only source that feeds the
  remote database.
- The Supabase MCP server is used in **read-only** mode for the remote project
  (queries, migration list, table inspection). DDL is prohibited via MCP.
- Every sync run is traceable in the GitHub Actions history with its backup artifact.

## D8 — Platform Extensions & Schema Drift Allowlist

**Decision:** The schema drift check (`scripts/check-schema-drift.sh`, used by
`scripts/db-reset-sync.sh` and both drift steps of `db-remote-sync.yml`) fails on
**any** statement printed by `supabase db diff` that is not listed in
`supabase/drift-allowlist.txt`. The allowlist is versioned and every entry carries
a comment explaining why it is tolerated.

**Extensions:**
- `hypopg` and `index_advisor` exist on the hosted project, so they are declared in
  `20261027000000_declare_platform_extensions.sql` and repo and remote match.
- `pg_net` is **not** installed on the hosted project and must not be. The CLI
  shadow database that `supabase db diff` builds always contains it, so the diff
  always proposes `drop extension if exists "pg_net";`. That single statement is
  the only allowlist entry (decision of 2026-10-27).

**Rules:**
- Drift is never excluded by pattern or by schema; only exact statements in the
  allowlist are tolerated.
- Adding an allowlist entry requires the reason in the file and an update to this
  section.
- `custom_access_token_hook` is enabled locally in `supabase/config.toml`. The
  hosted project's Auth hook configuration lives in the dashboard
  (Authentication → Hooks), is not part of the database, and is untouched by
  `db-remote-sync` resets.

## D9 — Remote Sync and the Access-Token Hook

**Decision:** The hosted project's `custom_access_token_hook` is disabled for the
whole duration of a `db-remote-sync` run and re-enabled only after a run ends green.
This applies to `reset` and `repair-push`; in `production` mode (D22) the hook
stays enabled, since nothing is dropped.

**Why:** a reset drops and recreates schema `public`, including the hook function and
the tables it reads. While the hook is enabled and missing or half-migrated, GoTrue
fails every sign-in and token refresh with "Error running hook URI". The hook setting
lives in the dashboard, not in the database, so the reset does not change it.

**Procedure:**
1. Dashboard → Authentication → Hooks → "Customize Access Token (JWT) Claims":
   **disable** the hook (Postgres → `public.custom_access_token_hook`).
2. Run `db-remote-sync` (`mode`, `CONFIRM`, optional `load_seed` / `owner_email`).
   The first and last steps of the workflow print this reminder.
3. Only if the run ends **green**: **re-enable** the hook, pointing at
   `public.custom_access_token_hook`.
4. **Sign out and sign in again.** Existing tokens were issued without the hook and
   carry no `tenant_id`; tenant-scoped policies return nothing until a new token is
   issued.

If the run fails, keep the hook disabled, fix the cause, and run the sync again.

### What happens when the seed fails on the remote

`supabase/seed.sql` runs inside a single transaction (`BEGIN … COMMIT`). If any
statement fails (constraint violation, missing dependency, etc.) the entire seed
is rolled back — the database keeps the schema applied by the migrations but
contains no demo data.

**Recovery:** fix the seed locally, verify with `supabase db reset`, push the fix,
and run `db-remote-sync` again with `load_seed: true`. Because the seed uses
`ON CONFLICT DO NOTHING` everywhere, re-running after a partial or rolled-back
load is safe and idempotent.

**CI safety net:** the `db-reset-test` job and the rehearsal phase both create the
demo auth user `f0000000-0000-0000-0000-000000000001` before loading the seed, so
conditional blocks guarded by `IF EXISTS (… auth.users …)` always execute and
constraint violations surface before the workflow touches the remote database.

## D10 — ARCO: Suppression (`anonymize_user`)

**Decision:** `anonymize_user(p_user_id, p_arco_request_id)` is the **final,
irreversible suppression step** of an ARCO cancellation, not its first step.

**Behaviour:**
- Requires a tenant admin (RBP v2) and a `cancelacion` request for that user in
  status `pending` or `in_progress`; refuses users already anonymized.
- `users`: name and email replaced by a random `ANON-xxxxxxxx` token (not derived
  from the user), `is_anonymized = true`, `status = TERMINATED`, `deleted_at` set.
- `ec_personal_information`: every personal column is cleared (name replaced by
  the token; date of birth, gender, marital status, nationality, identifiers,
  contact, address, country, emergency contact and event reason set to NULL).
- Personal values already present in the tenant's `audit_logs` (`diff`,
  `details_json`) are replaced with `[suprimido]`; the rows are kept.
- `audit_logs` records only the event: actor (`user_id`), time (`created_at`),
  subject (`entity_id`) and `arco_request_id`. No re-identification map exists.
- Kept: `users.id`, `auth_uid`, `employee_id`, `ec_job_information` (reporting
  line), all other ids and audit rows.

**Pendiente — Fase 20 (DRTM):** bloqueo previo a la supresión según la LFPDPPP 2025 y
plazos de conservación de LFT art. 804, LSS art. 15 y CFF. Validar plazos con
asesoría jurídica antes de operar con clientes reales. Mientras tanto, la
cancelación ARCO no debe ejecutarse en tenants productivos.

## D11 — Manual Project Settings and Privileged RPCs

**Manual settings (hosted project, not in migrations):** some Supabase Auth
settings live in the dashboard and are not reproduced by `db-remote-sync`:
- **Leaked password protection** (HaveIBeenPwned check): Dashboard →
  Authentication → Attack Protection (password security). Enabled manually by
  the project owner when the plan allows it. The `auth_leaked_password_protection`
  advisor stays until it is turned on.
- **Custom access token hook**: see D9.

**Privileged RPCs (SECURITY DEFINER, executable by `authenticated`):**
- `write_audit_log(...)`: ignores the tenant and actor it receives and always
  records `requesting_tenant_id()` and `current_app_user_id()`; fails for callers
  without tenant. `audit_logs` has no INSERT policy or privilege for `anon`,
  `authenticated` or `prisma_app`: entries are written only through this function.
- `insert_effective_record(table, user, data, start)`: only `ec_job_information`,
  `ec_compensation` and `ec_personal_information`; caller must hold app_role
  `owner` or `hr_admin` and the subject must belong to the caller's tenant;
  `tenant_id`, `user_id`, dates, ids and unknown columns are rejected in `data`;
  values are cast through `jsonb_populate_record`.

## Known Risk — Open SELECT on Permission Matrix Tables

**Status:** Accepted (temporary). Registered 2026-10-28.

**Tables affected:** `permission_roles`, `role_permissions`, `permission_groups`,
`role_grants`.

**Current RLS policies:** SELECT is open to every `authenticated` user within their
own tenant (filtered by `requesting_tenant_id()`). INSERT/UPDATE require
`is_tenant_admin()`. DELETE has no policy (soft-delete only).

**Why it exists:** The `can()` authorization function (RBP v2) runs Prisma queries
against `role_permissions` and `role_grants` from the application layer using the
caller's JWT. If SELECT were restricted to admins, non-admin users would lose
authorization resolution — every `can()` call would return `false`.

**Risk:** Any employee can read the full permission matrix of their tenant via the
Supabase client: role names, permission keys, actions, group memberships, and grant
scopes. This is an information disclosure issue — the structure of the RBAC model
is visible to unprivileged users.

**Planned fix (authorization hardening loop):**

1. Move `can()` evaluation to a `SECURITY DEFINER` PostgreSQL function that reads
   the permission tables with elevated privileges (bypassing RLS), receives the
   user ID, permission key, action, and optional target/field parameters, and
   returns a boolean. The application calls `SELECT can(...)` instead of querying
   the tables directly.
2. Restrict SELECT on `permission_roles`, `role_permissions`, `permission_groups`,
   `role_grants`, and `group_members` to `is_tenant_admin()`.
3. Unify `app_role` (JWT claim) with RBP v2 so that admin detection also runs
   through the permission chain instead of relying on a static role string.

## Known Risk — Integration Tests Use Raw SQL Instead of `can()`

**Status:** Accepted (temporary). Registered 2026-10-28.

**Affected tests:** `admin-center-authz.test.ts` — the `canViaRbp()` helper.

**Current state:** The integration tests verify the RBP permission chain
(`group_members` → `role_grants` → `role_permissions`) by querying the database
directly with a raw SQL `EXISTS` check. They do **not** call the application-level
`can()` function from `@/lib/authz/can.ts`.

**Risk:** If `can()` diverges from the raw SQL logic (e.g. adds caching, changes
the join order, introduces field-level or population-based filtering), the tests
will still pass while the real authorization path is broken.

**Planned fix (authorization hardening loop):**

1. Once `can()` is moved to a `SECURITY DEFINER` PostgreSQL function, the
   integration tests should call `SELECT can(...)` directly against the database,
   testing the same code path the application uses.
2. Alternatively, expose a thin HTTP endpoint or Server Action that wraps `can()`
   and have the integration tests call it with each user's token, exercising the
   full stack (JWT → Supabase client → `can()`).

## Known Risk — Admin Center Cannot Create or Edit Roles

**Status:** Accepted (temporary). Registered 2026-10-28.

**Affected component:** `apps/web/src/components/role-manager.tsx` — "Nuevo Rol"
button and role editing UI.

**Current state:** The Admin Center's "Gestionar Roles" page renders an expandable
list of roles, permissions, groups, and grants. The "Nuevo Rol" button opens a
modal, but the modal has no Server Action or API endpoint wired to it — submitting
does nothing. Editing existing roles (rename, add/remove permissions, change group
assignments) is similarly non-functional; the UI is read-only.

**Risk:** Administrators who expect to manage roles through the UI will find it
inoperable. Currently, role and permission changes can only be made via direct
database operations or migrations.

**Planned fix:**

1. Implement Server Actions for role CRUD (`createRole`, `updateRole`,
   `deleteRole`) gated by `admin.manage_roles:edit`.
2. Wire the "Nuevo Rol" modal and inline-edit controls to these actions.
3. Add integration tests that verify CRUD operations respect RBP guards.

## Known Risk — Denial Tests Do Not Assert Rows Exist Before Checking Zero

**Status:** Accepted (temporary). Registered 2026-10-29.

**Affected component:** `apps/web/__tests__/integration/admin-center-authz.test.ts`
and any integration test that asserts `expect(data ?? []).toEqual([])` as proof
that RLS denied access (e.g., `audit_logs`, `system_configurations`).

**Current state:** The denial assertions check that an employee's Supabase client
receives zero rows. However, the tests do not first verify that at least one row
exists for the tenant in that table. If the table happens to be empty, the test
passes vacuously — it proves nothing about the RLS policy.

**Risk:** A migration could silently drop the INSERT policy or the seed data that
populates the table, and the denial tests would still pass, masking a real RLS
regression.

**Planned fix:**

1. Before each denial assertion, run a positive-control query with the admin
   client (`tenant.admin.client`) confirming `data.length > 0` for the same
   table and tenant.
2. Alternatively, insert a known row in `beforeAll` and assert it is visible
   to the admin but not to the employee.

## Known Risk — Integration Tests Duplicate Script SQL Instead of Running It

**Status:** Accepted (temporary). Registered 2026-10-30.

**Affected tests:** `__tests__/integration/link-owner.test.ts` and the seed
fixture in `__tests__/integration/helpers/world.ts` (`createTenant`).

**Current state:** The link-owner integration test contains a `linkOwnerSql()`
helper that reproduces the SQL from `scripts/link-owner.sh` as parameterized
queries in TypeScript. Similarly, the seed setup in `world.ts` replicates
parts of `supabase/seed.sql` manually. Neither test actually invokes the
original script or seed file.

**Risk:** If the script or seed drifts (new columns, changed role names,
additional inserts), the test's copy stays stale and gives a false green.
The Employee role name mismatch (`'employee'` vs `'Employee (Self-Service)'`)
was an instance of this drift.

**Planned fix:**

1. `link-owner.test.ts` should shell out to `bash scripts/link-owner.sh`
   with the test DB URL and assert the results, instead of duplicating SQL.
2. The seed fixture should run `psql -f supabase/seed.sql` or source the
   relevant blocks, not hand-write equivalent INSERT statements.

## Known Risk — ~35 Supabase Queries Ignore Returned Errors

**Status:** Accepted (temporary). Registered 2026-10-30.

**Affected files:** ~15 files across `apps/web/src/`, primarily in page
components (`employees/page.tsx`, `dashboard/page.tsx`, `profile/page.tsx`,
`admin-center/page.tsx`, etc.) and some Server Actions.

**Current state:** Many `.from(...).select(...)` calls destructure only
`{ data }` and never check `error`. A failed query silently returns `null`
data, rendering an empty page or quietly skipping logic instead of surfacing
the problem.

**Risk:** RLS misconfigurations, network issues, schema changes, or
PostgREST errors are masked. The user sees an empty list and assumes there
is no data, when in fact the query failed.

**Planned fix:**

1. Add a shared `assertSupabaseResult()` helper that throws on non-null
   `error` and returns typed `data`.
2. Wrap existing queries incrementally, starting with the pages that
   display employee or configuration data.
3. Add error boundaries or toast notifications for query failures.

## Known Risk — ARCO Self-Service Not Yet Implemented

**Status:** Accepted (deferred to DRTM phase). Registered 2026-10-30.

**Current state:** The "Derechos ARCO" menu item is visible to all
authenticated users, but every Server Action (`createArcoRequest`,
`processArcoRequest`, `exportUserData`) gates access with
`can(actorId, "arco.manage", "view")`, which only admin roles hold. An
employee who clicks the menu sees an empty page or an error.

**Risk:** Employees cannot exercise their ARCO rights (access, rectification,
cancellation, opposition) through the UI. The menu entry creates the
expectation of self-service that the system does not deliver.

**Planned fix (DRTM — Data Retention & Transparency Module):**

1. Split permissions: `arco.request` (employee: create and view own requests)
   vs `arco.manage` (admin: process all requests).
2. Add a self-service form where the employee creates a request for their own
   data, scoped by `target_population = 'self'`.
3. Hide or disable the admin processing UI for non-admin roles.
4. Gate the menu visibility by `can(actor, "arco.request", "view")` so it
   only appears for users who can do something with it.

## Known Risk — Dual Admin Truth (RBP vs. JWT app_role)

**Status:** Accepted (permanent). Registered 2026-10-31.

**Affected components:**

- `supabase/migrations/20261030010000_ec_job_info_restrictive_admin.sql` — RESTRICTIVE
  RLS policies that call `is_tenant_admin()`, which checks RBP (`role_grants` +
  `permission_roles.is_admin_role` + `group_members`).
- `insert_effective_record()` (SECURITY DEFINER RPC) — checks `has_app_role('owner')
  OR has_app_role('hr_admin')`, which reads `app_role` from the JWT claim
  (`request.jwt.claims`).

**Current state:** There are two independent "is this user an admin?" checks:

1. **RBP-based** (`is_tenant_admin()`): looks up group membership → role grants →
   `is_admin_role` flag on the permission role. Used by RESTRICTIVE RLS policies.
2. **JWT-based** (`has_app_role()`): reads the `app_role` string from
   `user_tenant_memberships` (set at login, baked into the JWT). Used by
   `insert_effective_record()`.

Both must pass for an INSERT/UPDATE on `ec_job_information` to succeed via the
RPC: `insert_effective_record()` rejects non-admins before the SQL runs, and
the RESTRICTIVE policy rejects the row if `is_tenant_admin()` returns false.

**Risk:** If the two sources diverge (a user has the JWT `app_role='owner'`
but is not in any admin group in RBP, or vice versa), writes will fail even
though one system considers them authorized. `createTenant()` and `link-owner.sh`
keep both in sync for new tenants, but manual edits to `group_members` or
`user_tenant_memberships` without updating the other will break the invariant.

**Mitigation:** Integration test `insert-effective-record-rls.test.ts` verifies
that the path works end-to-end for owner and is blocked for employee. A future
unification (making `insert_effective_record()` also check RBP, or replacing
`app_role` with RBP entirely) would eliminate this risk.

## D14 — Per-Request Permission Context (Pool Exhaustion Fix)

**Decision:** `can()` loads all permission data (grants, role_permissions,
module flags) in a **single** `withTenant` transaction per request, memoized
with `React.cache()`. Subsequent `can()` calls within the same RSC render
evaluate against the preloaded context without opening additional transactions.

**Problem:** `layout.tsx` called `Promise.all(keys.map(k => can(..., k, ...)))`,
opening one `withTenant` transaction per key. With 6+ sidebar keys and a
connection pool limit of 5 (PgBouncer transaction mode), every request
exhausted the pool: `Unable to start a transaction in the given time`.

**Architecture:**

1. `loadPermissionContext(userId, tenantId)` — ONE `withTenant` call that
   fetches tenant flags, user grants, and role permissions with `Promise.all`
   inside the transaction (one connection, three queries).
2. `loadPermissionContextCached = cache(loadPermissionContext)` — React
   `cache()` ensures this runs at most once per RSC request. It is **not**
   cached between requests: each incoming HTTP request gets a fresh context.
3. `evaluateFromContext(ctx, ...)` — pure synchronous evaluation: module
   gate, grant check, permission match. No DB calls.
4. `evaluateTargetPopulation(ctx, ...)` — for `same_department` and
   `direct_reports`, opens ONE additional `withTenant` to check the
   org-structure condition.
5. `canMany(userId, keys, action)` — batch evaluation for layout and lists.
   Loads context once, loops through keys synchronously. Returns
   `Map<string, CanResult>`.

**Why not cached between requests:**
- `React.cache()` is scoped to one React Server Component render. The cache
  is discarded at the end of the request.
- A permission revoked between requests takes effect immediately on the
  next render — there is no stale window.
- No global `Map`, no TTL, no manual invalidation needed.

**Transaction timeouts:** `withTenant` now accepts explicit `maxWait` and
`timeout` parameters via environment variables (`PRISMA_TX_MAX_WAIT`,
`PRISMA_TX_TIMEOUT`), defaulting to 5s and 10s respectively.

**Since D47:** the context is one call to `rbp_context()` and the population
check one call to `rbp_target_in_population()`, both only for `prisma_app`;
there is no `withTenant` transaction any more. The per-request memoization and
`canMany()` are unchanged.

## D17 — Local Container Stack and Worker Queue

**Decision:** Phase 9a runs the app locally as two containers, web (Next.js
standalone) and worker (pg-boss consumer), on top of the Supabase CLI stack.
`npm run local:up` is the single entry point. Nothing here is paid (Roadmap,
Principle 8).

**Images:**
- `apps/web/Dockerfile`: multi-stage with `turbo prune @scaliahr/web --docker`,
  Node 22 Alpine, `output: "standalone"`, non-root `nextjs` user, `HEALTHCHECK`
  on `/api/health`. Only `NEXT_PUBLIC_SUPABASE_URL` and
  `NEXT_PUBLIC_SUPABASE_ANON_KEY` are build arguments (Next.js inlines them in
  the browser bundle, so they are public by design); every secret is runtime
  environment.
- `apps/worker/Dockerfile`: same pruning, compiled TypeScript, production
  dependencies only, non-root `node` user, no build arguments.
- `.dockerignore` keeps every `.env*` file out of the build context. The CI
  `docker` job checks that both images run as non-root and carry no
  secret-like variables or `.env` files. Images are built, never pushed
  (publishing is Phase 23).

**docker-compose.yml:** only `web` and `worker`. Both join the Supabase CLI
network, which `scripts/local-up.sh` discovers from the database container and
passes as `SUPABASE_NETWORK`; there the CLI's containers answer as `db` and
`kong`. Web publishes `127.0.0.1:3000` only (D4). Local credentials live in
`.env.docker` (git-ignored; template `.env.docker.example`).

**Server-side Supabase URL:** inside a container, `NEXT_PUBLIC_SUPABASE_URL`
(`http://localhost:54321`, what the browser uses) points at the container
itself. `lib/supabase/server-url.ts` makes the server and middleware clients use
`SUPABASE_INTERNAL_URL` (`http://kong:8000`) while keeping the cookie name
derived from the public URL (`sb-<host>-auth-token`), so browser and server
share the session. The CSP `connect-src` adds the configured Supabase origin
when it is not a hosted `*.supabase.co` project.

**`/api/health`:** public by design: no session, excluded from the middleware
matcher, and outside `(protected)`, so the authz coverage test does not apply.
It returns `{ status, checks: { app, database } }` with 200 or 503 and
`Cache-Control: no-store`, runs `SELECT 1` through the `prisma_app` connection
with a 2 s timeout, and never returns or logs error messages, hosts or
connection strings.

**`scripts/local-up.sh`:**
1. Starts Supabase local.
2. Aborts unless the database URL is `127.0.0.1` or `localhost` with no query
   string (`scripts/lib/local-db-guard.sh`).
3. Sets local-only passwords for `prisma_app` and `worker_app`
   (`scripts/set-local-role-passwords.mjs`, which checks the URL again).
4. Builds and starts both containers.
5. Smoke-tests `/api/health` and one `system.ping` job.

It never runs against a remote project.

**Worker queue (pg-boss 12.38.0, schema version 46):**
- Schema `pgboss` comes only from
  `supabase/migrations/20261104010000_d17_worker_queue_pgboss.sql` (D1),
  generated with `npm -w @scaliahr/worker run pgboss:sql`. pg-boss is pinned
  exactly. Upgrading it requires a new migration
  (`pgboss:sql -- migrate <current version>`): `pgboss-security.test.ts` fails
  while the database schema version differs from the installed package.
- Queues are declared only in migrations and are never partitioned, so they
  live in the shared job table and need no per-queue DDL. Current queues:
  `system.ping` (2 retries with backoff, dead letter) and `system.dead_letter`.
- The worker never runs DDL. `migrate`, `createSchema`, `schedule`, `reindex`
  and `persistQueueStats` are off (`apps/worker/src/boss.ts`). Cron scheduling
  stays off because pg-boss's timekeeper declares its internal
  `__pgboss__send-it` queue on every start; scheduled jobs need a migration
  that declares that queue and an explicit decision on how the worker may
  insert it.
- The construction plans create `queue_stats` partitions named after the day
  they run. The migration drops them so the schema does not depend on the date
  it is applied (queue stats stay off).
- `worker_app`:
  - LOGIN, NOBYPASSRLS; no CREATE on any schema or on the database; owns
    nothing.
  - DML on `pgboss` tables, except INSERT and DELETE on `queue` and `version`.
  - No EXECUTE on `create_queue` or `delete_queue`.
- Every `pgboss` table has ENABLE + FORCE RLS, with policies only for
  `worker_app` and `postgres` (the migration owner). `anon`, `authenticated`,
  `service_role` and `prisma_app` have no access, and PostgREST does not
  expose `pgboss`.
- The `worker_app` password is set by `local-up.sh` locally and by
  `supabase-test-env.sh` for tests. On hosted projects it will be a secret
  (Phase 23, like `PRISMA_APP_PASSWORD`).
- `db-reset-sync.sh` (reset mode) drops `pgboss` together with `public`, since
  migrations recreate both.

**Pending:** `pgboss` functions keep pg-boss's mutable `search_path`; review
them with the Phase 9b advisors work (done: D25 fixes it). The first real jobs
arrive with Phase 9a: email in PR 2 (D20), per-tenant exports in PR 4.

## D18 — Theming por tenant

**Decision:** each tenant picks one of six presets and adds its brand within
fixed limits, from the Theme Manager in Admin Center (Roadmap, Phase 11).

- A job with an invalid payload retries five times before reaching the dead

- Until Phase 11 brings uploads (D18), a tenant admin can point the logo at any

## D21 — Tenant Resolution by Subdomain or Company Code

**Decision:** a request names its tenant with the host, `<slug>.<app host>`
(`acme-corp.localhost` locally, `<cliente>.scaliahr.com` in Phase 23), or, on
the app host itself, with the company code chosen at login. The middleware
lets a signed-in user through only when that tenant is the one in their token
and it is not suspended. Phase 9a, PR 2.

**Resolution (`apps/web/src/lib/tenant/host.ts`):**
- The app host comes from `APP_BASE_URL` (default `http://localhost:3000`).
- A subdomain always wins; the company code (`scalia_company` cookie) only
  counts on the app host. Other hosts name no tenant.
- The login page asks for the company code (optional) only on the app host.
  `rememberCompanyCode` validates its format with zod and stores it in an
  httpOnly cookie; it never checks that the company exists.

**Enforcement (`lib/supabase/middleware.ts`), for signed-in users on
non-public paths:**
- With a requested tenant, look it up by slug with the user's own session.
  RLS on `tenants` shows each user only their own tenant, so another tenant,
  an unknown slug and a failed lookup all return nothing.
- Without one, look up the token's tenant by id, so a suspended tenant is
  refused on the app host too.
- Access requires the row's id to equal the token's `tenant_id` and
  `suspended_at` to be null. Any refusal returns the same 404 page (no-store,
  no tenant name), before the MFA check, and keeps refreshed session cookies.
- Anonymous visitors get the same login redirect on any host, and public paths
  (`/login`, `/auth`, `/signup`) are served on any host without a lookup, so
  nobody can learn from the response whether a tenant exists.

**Suspension (`20261104020000_d21_tenant_suspension.sql`):**
`tenants.suspended_at`, set only by the platform: the owner's column-level
UPDATE grant does not include it. `custom_access_token_hook` skips suspended
tenants in both of its lookups, so the next token of their users carries no
tenant (or another active membership) and RLS hides the tenant's rows.
`email_branding` returns no row for them, so their emails are dropped (D20).

**Tests:** unit tests for host parsing, the access decision, the 404 and the
company-code action; integration tests that run the real middleware with real
sessions against the local stack: own subdomain allowed, another tenant's
subdomain or company code refused, nonexistent and suspended tenants answered
exactly alike, the same login redirect for anonymous visitors, the host
winning over the company code; and tests of the hook and the column grant.

**Accepted for now:**
- A token issued before the suspension keeps its `tenant_id` until it expires
  (`jwt_expiry` = 900 s). The middleware refuses it at once, but direct Data
  API calls with that token still pass RLS until then.
- Each signed-in request on a protected path makes one `tenants` lookup.
- Users with memberships in several tenants (support access, D13) are refused
  on any tenant but their active one; switching tenant does not move them to
  the other subdomain yet (Phase 12).
- Custom domains (`tenants.domain`) are not resolved yet (Phase 23).

## D22 — Safe Migrations: Production Mode and Expand/Contract

**Decision:** production only ever receives pending migrations, in order, while
the app keeps serving traffic. `db-remote-sync` gains a `target` input (`dev`,
`staging`, `production`) and a `production` mode; `reset` and `repair-push` are
refused for production at three levels. Every migration must be backward
compatible (expand/contract). Phase 9a, PR 3. Nothing remote is created:
staging and production, with their GitHub environments
(`remote-db-staging`, `remote-db-production`), arrive in Phase 23; `dev` keeps
the existing `remote-db` environment.

**Production mode (`scripts/db-migrate-sync.sh <db-url> <target>`):**
1. Lists the pending migrations (`supabase db push --dry-run`).
2. Applies them with `supabase db push`, without `--include-all`: a migration
   older than the last applied one is refused instead of running out of order.
3. Never truncates or repairs `supabase_migrations.schema_migrations` and never
   drops a schema, so a history that differs from `supabase/migrations` stops
   the run.
4. Checks that the history holds as many versions as there are migration files.
5. For target `production`, writes the production marker.

The workflow keeps the pre-sync backup (D7), rehearses on a fresh local stack
(every migration plus the integration tests), then runs the drift and
critical-object checks on the remote. Seeds and `owner_email` are refused for
production. Applying the pending migrations to a copy of production is the job
of the staging run before promotion (D15).

**Reset blocked for production, three levels:**
- `scripts/lib/db-sync-guard.sh` holds the policy: production accepts only the
  `production` mode, and unknown targets or modes are refused. The workflow
  runs it before any other step, and `db-reset-sync.sh` (which now requires a
  target) runs it before its first statement.
- The database marks itself: `ops.production_marker` (one row at most,
  ENABLE + FORCE RLS, no application role can see schema `ops`) is written by
  the first production-mode sync. `reset` and `repair-push` refuse any
  database that has it, whatever target the run claims, and also refuse when
  the marker cannot be read. This covers a production URL configured in the
  wrong environment.
- The destructive remote steps of the workflow carry
  `inputs.target != 'production'` in their conditions.

A brand-new production project has no marker until its first production-mode
sync; until then only the target check protects it.

**Tests (local only):**
- `__tests__/scripts/db-sync-guard.test.ts` covers the policy matrix. It shows,
  with stubbed `psql` and `supabase`, that a refused reset runs no command, or
  only the marker check. It also checks the workflow's guard order and step
  conditions.
- `__tests__/integration/db-sync-modes.test.ts` runs against Supabase local:
  - production mode is a no-op when up to date;
  - it applies exactly one pending migration without touching data;
  - it refuses an out-of-order migration and a divergent history without
    repairing it;
  - reset is refused for target production;
  - once a production-mode sync has marked the database, a reset with target
    `local` is refused and the database is unchanged.

**Expand/contract rule.** In production mode the old version of the app runs
against the new schema during the deploy, and a rollback to the previous image
(runbook, PR 4) runs the old code against it for good. So:
- **Expand** (any release): add tables, nullable columns or columns with a
  default, indexes, functions, policies and queues; widen a check constraint.
- **Migrate** (code): ship code that works with both shapes: write both, read
  the new one with a fallback. Backfill in batches, from a worker job for large
  tables.
- **Contract** (a later release, once no running or rollback image uses the old
  shape): drop columns, tables and functions, rename, `SET NOT NULL`, narrow
  types or constraints.
- Never in a single release: renaming a column or table, changing a column's
  type, dropping something the running version reads, adding `NOT NULL`
  without a default to an existing table, or changing a function's signature in
  place. Create the new function and drop the old one in a contract step;
  `CREATE OR REPLACE` with the same signature is fine (D21 did this with the
  hook).
- Security fixes (revoking a privilege, tightening RLS) may break the old
  version on purpose and ship at once.
- A contract migration names, in its header, the expand migration it completes
  and the release since which the old shape is unused.
- pg-boss upgrades (D17) follow the same rule.

The rule is checked by review in each PR; there is no automated check yet.

## D23 — Backups and Restore (Local)

**Decision:** two kinds of backup, both tested against Supabase local in CI on
every PR. A per-tenant logical export runs in the worker and restores one tenant
without touching the others. A full logical backup restores the whole database
in place. Both stay local until Phase 23 (Roadmap, Principle 8). Phase 9a, PR 4.
Operator steps are in `docs/RUNBOOK.md`.

**Per-tenant export (worker, `backup.tenant_export`):**
- Queue declared in `20261104050000_d23_tenant_backup.sql`: 2 retries with
  backoff, then the dead letter queue. Data `{ tenantId }`, validated with zod.
  `node dist/export-tenant.js <tenant-id>` inside the worker container enqueues
  one and waits.
- `worker_app` still reads no `public` table directly. It uses three functions
  that only it can execute:
  - `tenant_backup_tables()` lists the scope: the tenant row, every table with
    `tenant_id` (from the catalog, so new tables are included automatically) and
    the child tables `talent_pool_entries` and `succession_nominees` through
    their parent.
  - `tenant_export_rows(tenant, table)` (SECURITY DEFINER, empty `search_path`)
    refuses any table outside that list.
  - `backup_schema_version()` gives the schema version.
- Not exported: `rate_limits` (transient), `user_settings` (per account),
  `auth` accounts (in the full backup) and `pgboss` jobs. A test fails when a
  `public` table is neither in the scope nor in that list.
- File `<BACKUP_DIR>/tenants/<tenant>/<time>.export.gz`, mode 0600, written to
  `.partial` and renamed only when complete. Lines are `#manifest` (format,
  version, tenant, schema version, time, tables), then `<table>\t<row JSON as
  printed by Postgres>` (numbers are never parsed, so no precision is lost),
  then `#end` (counts, total, SHA-256 of the row lines).
- Locally `BACKUP_DIR` is the `scaliahr_backups` volume. The adapter boundary
  is the directory, so Phase 23 swaps it for private encrypted storage.

**Per-tenant restore (`scripts/restore-tenant.mjs`, operator, local database
only):**
- Checks the file (format, SHA-256, counts), that its tenant is the one
  requested, that its schema version equals the database's and that the table
  list matches.
- Then, in one transaction with `session_replication_role = replica`, replaces
  every row of that tenant in the covered tables with the exported ones. Before
  committing it checks every foreign key of `public` and every count, and rolls
  back on any mismatch.
- Audit log stays append-only in spirit: entries written after the export are
  kept when their user exists after the restore. The others (users created
  after the export) cannot stay because of the foreign key; they go to a JSON
  report next to the export, so nothing disappears silently.

**Full backup (`scripts/backup-full.sh`) and restore
(`scripts/restore-full.sh`):**
- `pg_dump` runs inside the Supabase database container, so it always matches
  the server version, and it can only reach the local stack.
- `app.dump`: `public`, `pgboss` and `ops` with structure, data and grants.
- `platform.dump`: data of `auth.users`, identities, MFA factors, recovery codes
  and passkeys, plus the migration history. Sessions and tokens are left out.
- `manifest.json`: schema version and SHA-256 of both files.
- The restore refuses a checksum mismatch, a schema version other than this
  checkout's last migration, or a running web or worker container.
- It then drops `public`, `pgboss` and `ops`, truncates the accounts and the
  history, and restores accounts first and application schemas second. All of
  this runs in a single `psql --single-transaction`, so a failure leaves the
  database as it was.

**Tests (CI, `apps/worker/__tests__/integration/backup.test.ts`):**
- scope classification, function privileges and table-name injection;
- the worker's export holds only its tenant's rows, numbers exact;
- a missing tenant fails the job and writes nothing;
- refusals change nothing: another tenant's file, a corrupted file, a remote
  URL, another schema version, a corrupted dump;
- a damaged tenant is restored to the export, with audit entries kept or moved
  to the report, while another tenant and the demo tenant stay identical;
- after deleting every tenant, an account and part of the history, a full
  restore brings back an identical database (row counts and content hashes of
  every table).

**Accepted for now:**
- The export and the restore read each table into memory: fine for local
  tenants, to be streamed before large customers (Phase 23).
- The restore leaves no entry in the tenant's audit log, which needs a user of
  that tenant. The JSON report is the record until the platform console has its
  own audit (Phase 12).
- Storage objects (Phase 11 uploads) are not covered yet.

## D24 — Local Rollback and Runbook

**Decision:** rolling back the local stack means restarting the previous images;
the schema is never rolled back. Phase 9a, PR 4. Steps in `docs/RUNBOOK.md`.

- `npm run local:up` tags the images it is about to replace as `:previous`,
  labels new images with `org.opencontainers.image.revision` (git describe) and
  applies pending migrations only (`supabase migration up --local`, the local
  counterpart of D22's production mode).
- `npm run local:rollback` (`local-up.sh --rollback`) retags `:previous` as
  `:local` and keeps the replaced images as `:rolled-back`. It restarts web and
  worker without building and runs the same smoke checks (health, ping, email).
  Without a `:previous` image it stops before changing anything.
- The previous image runs against the newer schema because every migration is
  expand/contract (D22). Data damage is handled by restoring a backup (D23),
  not by the image rollback.
- The CI `docker` job runs the drill: `local:up` twice, then `local:rollback`,
  and checks that both containers run the `:previous` image. It also runs a
  per-tenant export inside the running worker.
- Phase 23 completes the runbook with the Railway rollback and the hosted
  restore procedures.

## D25 — Database Hardening: Privileges and Advisors

**Decision:** app roles hold only the table privileges the app uses, the audit
log is insert-only for them, and the Supabase advisors report nothing on the
local database, checked in CI. Phase 9b, PR 1
(`20261105010000_d25_db_hardening.sql`).

**Privileges:**
- `anon`, `authenticated` and `prisma_app` lose `TRUNCATE`, `TRIGGER`,
  `REFERENCES` and `MAINTAIN` on every `public` table. `prisma_app` held them
  through its membership in `authenticated`. Supabase grants them by default,
  the app uses none, and each one gets around RLS:
  - `TRUNCATE` empties a table ignoring RLS;
  - `TRIGGER` attaches code to other users' writes;
  - `REFERENCES` lets a foreign key pin another tenant's rows;
  - `MAINTAIN` (PostgreSQL 17) allows `LOCK TABLE`, `VACUUM` and `REINDEX`.
- The default privileges of `postgres` in `public` drop them too, so later
  migrations start without them.
- `service_role` keeps them. It bypasses RLS by design and is never used by
  the app (D4).
- `pgboss` and `ops` already granted nothing of the sort.
- `db-reset-sync.sh` still recreates Supabase's default grants before pushing
  the migrations, and this migration narrows them again.

**Audit log:** `audit_logs` is written only through `write_audit_log`; direct
inserts were already rejected. RESTRICTIVE policies already blocked UPDATE and
DELETE, and `TRUNCATE` is now gone. Tests cover the tenant owner through the
Data API and an app connection acting as `authenticated` with tenant claims.
The only exception remains the ARCO suppression of D10, inside the database.

**Advisors (`supabase db advisors`, security and performance):**
- pg-boss functions get `search_path = ''`, closing the item D17 left open.
  Their bodies are fully qualified. A pg-boss upgrade that recreates them must
  repeat the `ALTER FUNCTION`; the check below fails until it does.
- Covering indexes for the three pg-boss foreign keys. Their names start with
  `d25_` because pg-boss names its own indexes `job_iN`.
- `rate_limits` keeps no direct grants for app roles and gets an explicit
  RESTRICTIVE deny-all policy. Access stays through `check_rate_limit()` (SECURITY DEFINER).
  D28 replaces it with `rate_limit_consume()`, which only `prisma_app` can call.
- `scripts/check-advisors.mjs` (`npm run db:advisors`, and an integration test
  in CI) fails on any finding except `unused_index`. That lint reads index usage
  statistics, so on a freshly migrated database every index looks unused; index
  usage is reviewed with the load-test data in a later 9b PR.

**Tests:** `__tests__/integration/db-privileges.test.ts`:
- no risky privilege for any app role in `public`, `pgboss` or `ops`;
- a new table starts without them;
- `TRUNCATE` refused from an app connection;
- the audit log cannot be changed, deleted or truncated;
- `rate_limits` is reachable only through the function;
- the advisors check passes.

## D26 — CI: Supabase Images from the Actions Cache

**Decision:** CI keeps the Supabase local images in the GitHub Actions cache
instead of pulling them from `public.ecr.aws` on every run. ECR's anonymous rate

  `ci.yml`. `local-up.sh` reads `SUPABASE_EXCLUDE` when set; CI also leaves
  Studio out, and developers keep it.

## D27 — Safe Errors and JSON Logs

**Decision:** no database, service or Auth error message reaches the user. The
detail goes to structured JSON logs with the request id and tenant id, sensitive
data masked; the user sees a generic message with a code to quote. Error
reporting sits behind an adapter that writes those logs locally; Sentry plugs
into it in Phase 23. Phase 9b, PR 2.

**Request and tenant ids (`src/middleware.ts`, `lib/supabase/middleware.ts`):**
- Every request gets a fresh `x-request-id` (UUID), returned as a response
  header and forwarded to the page or Server Action. An id sent by the client
  is always replaced.
- `x-tenant-id` is forwarded only from the verified token's `tenant_id`. A
  value sent by the client is deleted. Both headers are for logs only, never
  for authorization.
- `/api/health` and static assets stay outside the middleware and get no id.

**Logs (`lib/log`):**
- `log(level, event, fields, ctx)` writes one JSON line: `time`, `level`,
  `event`, `requestId`, `tenantId` and the fields. It works on the Node and
  Edge runtimes.
- `redact()` blanks sensitive keys at any depth: passwords, secrets, tokens,
  authorization, cookies, API keys, CURP, RFC, NSS, CLABE, salary and bank
  fields. Inside free text it masks JWTs, bearer tokens, CURP, RFC, CLABE, card
  numbers and NSS, because database errors quote the offending values.
- The worker writes the same kind of JSON lines (`apps/worker/src/log.ts`)
  with the job id and the tenant id of the job. It never logs payloads, and
  error messages get the same masks. The operator CLIs (`smoke.js`,
  `export-tenant.js`) keep plain text.

**Errors:**
- `reportError(event, error, ctx)` goes through an `ErrorReporter`: the JSON
  log reporter now, Sentry in Phase 23 via `setErrorReporter`.
- `safeError(event, error, message?)` is the only way a Server Action or page
  turns an error into text. It reports the error with the request context and
  returns the generic message plus `Código: <request id>`. It replaces the 21
  places that returned `error.message` from Supabase or Postgres:
  - ARCO, employee changes, performance, skills hub, tenant switch, the
    employees list;
  - `createTenant`;
  - the unused MFA helpers.
- `createTenant`'s mapped messages (user already in a tenant, duplicate slug)
  remain, because they are ours.
- The audit-log helper, the LMS sync and `/api/health` report through the same
  logger. The LMS sync no longer returns Moodle's messages to its caller.
- Unhandled errors (server components, route handlers, Server Actions that
  throw) are reported by `instrumentation.ts` (`onRequestError`). The report
  carries the request id, tenant id, method, path without query string, route
  type and Next.js's digest.
- `app/error.tsx` and `app/global-error.tsx` show a generic message and the
  digest; never the message or the stack.
- Login and MFA ran in the browser against Supabase Auth; since D28 they run
  in Server Actions. `lib/auth/messages.ts` maps their errors to generic
  Spanish messages, telling only 429 (too many attempts) apart from "wrong
  credentials or code".
- Zod issue messages are still returned: they are our own validation texts.

**Tests:**
- unit tests for redaction, the logger, the reporter adapter, `safeError`,
  `onRequestError` and the middleware ids (fresh, never the client's, tenant
  only from the token);
- `__tests__/static/no-error-leaks.test.ts`, which fails on any
  `error: x.message`, `setError(x.message)` or `{x.message}` in `src`;
- an integration test for a forced error: a real session through the real
  middleware, then a real Postgres error quoting an RFC through `safeError()`.
  The JSON line carries the request id and the token's tenant id with the RFC
  masked, and the user gets only the generic message and the code;
- worker unit tests for its JSON lines and masks.

**Accepted for now:**
- Next.js also prints its own non-JSON line for unhandled errors.
- The digest in `error.tsx` is the user's reference for rendering errors; the
  logs pair it with the request id.
- Audit-log diffs keep the changed values (salary, personal fields) as the
  record of the change; masking them for readers is part of the Phase 11
  sensitive-data work.
- The employees search built a PostgREST `or()` filter from the raw search
  text, so commas or parentheses in it could add conditions (RLS still limited
  the rows to the user's tenant). Fixed in D28.

## D28 — Rate Limiting

**Decision:** every attempt to sign in, verify MFA, create a tenant, run a
Server Action or call an HTTP route spends a token of a Postgres-native limiter
first. The web server calls it through `prisma_app`, so it works before a
session exists and no Data API client can drain or reset a bucket. Login, MFA
and tenant creation fail closed; the rest fail open. Phase 9b, PR 3. No new
service: the limiter is a table and a function in the database (Principle 8).

**Database (`20261105020000_d28_rate_limiting.sql`):**
- `rate_limit_consume(key, action, max, window, tenant_id)` spends one token
  in a fixed window per (key, action) and returns 0 when allowed, or the
  seconds until the window resets (the Retry-After value). With a tenant id, the
  tenant's own limit for that action replaces the default. About one call in a
  hundred deletes windows older than a day, the longest window allowed.
- EXECUTE only for `prisma_app`: revoked from `PUBLIC`, `anon`, `authenticated`
  and `service_role`, which Supabase grants by default.
- `check_rate_limit()` is dropped. It answered only allowed/denied and any
  signed-in user could call it with any key. Expand/contract: no image called
  it (`lib/rate-limit.ts` had no callers).
- `tenant_rate_limits` (tenant, action, max, window): only `write` and `api`,
  with bounds (1–600 tokens, 10–3600 s) so a tenant cannot switch limits off.
  ENABLE + FORCE RLS; tenant admins read, insert and update their own tenant;
  no DELETE policy. It has a `tenant_id`, so tenant exports include it (D23).

**Policies (`lib/rate-limit.ts`):**

| Bucket | Key | Limit | If the limiter fails |
|--------|-----|-------|----------------------|
| `login_ip` | client IP | 20 / 60 s | refuse |
| `login` | requested tenant + email | 5 / 60 s | refuse |
| `mfa_verify` | tenant + user | 5 / 60 s | refuse |
| `tenant_create` | user | 3 / 3600 s | refuse |
| `write` | tenant + user (IP before a session) | 30 / 60 s, per tenant | allow |
| `api` | tenant + user (IP before a session) | 30 / 60 s, per tenant | allow |

- Keys are SHA-256 hashes of the bucket name and its parts: `rate_limits`
  stores no email or IP.
- The client IP is the last `X-Forwarded-For` hop, the one the proxy in front
  of the app writes. Only `login_ip` uses it; the account and user buckets do
  not depend on the IP.
- A refused Server Action returns "Demasiados intentos. Intenta de nuevo en N
  segundos." Next.js does not let a Server Action set its HTTP status. HTTP
  routes answer 429 with `Retry-After`. Each refusal writes a
  `rate_limit.blocked` JSON line (D27).
- When a fail-closed check cannot reach the limiter, the answer is "No se pudo
  procesar la solicitud" with a 30 s wait, and the error is reported.

**Where:**
- Login is the `signIn` Server Action. It checks `login_ip`, then `login`,
  before Supabase Auth sees the password. It signs in on the server (session
  cookies set there) and writes `AUTH_LOGIN` itself. A failed sign-in writes an
  `auth.login_failed` JSON line with the status only.
- MFA verification is the `verifyMfa` Server Action: zod on the factor id and
  the 6-digit code, the `mfa_verify` bucket, `challengeAndVerify` on the server,
  and `MFA_VERIFY` / `MFA_VERIFY_FAILED` written by the server.
- `createTenant` spends a `tenant_create` token after the user check.
- Every other exported Server Action starts with `limitWrite()` (ARCO,
  employee changes, performance, skills hub, tenant switch and revoke, company
  code, MFA enrollment audit, Admin Center). `/lms/launch` starts with
  `limitApi()`.
- `/api/health` is not limited: it is a healthcheck, and the limiter would cost
  the same database round trip as the check it protects.
- Admin Center shows "Límites de solicitudes" to `admin.manage_config:edit`.
  `updateTenantRateLimit` validates with zod (same bounds as the table),
  requires AAL2, upserts under RLS and writes `RATE_LIMIT_UPDATED`. Login, MFA
  and tenant creation keep the platform's limits: they protect authentication
  itself, and before a session the tenant is not verified.

**Supabase Auth native limits:** `[auth.rate_limit]` in `supabase/config.toml`
writes down the values the hosted project must carry (email 2/h,
token_refresh 150, sign_in_sign_ups 30, token_verifications 30 per 5 min…),
so a CLI upgrade cannot change them silently. Locally GoTrue receives them
but does not enforce the per-IP ones: the CLI sets no rate-limit header, and
without one GoTrue skips them. Checked: 170 wrong passwords in a row against
local Auth got no 429. Locally, the app's limiter is the one that acts.

**Employees search filter:** `lib/postgrest/filters.ts` builds `.or()` values
inside double quotes (with `\` and `"` escaped), where `,` `.` `:` `(` `)` are
plain text, and escapes the LIKE wildcards. `*` is dropped, because PostgREST
turns it into `%`. The search text is validated with zod (trimmed, at most 100
characters, page ≥ 1). `performance/page.tsx` uses the same builder. A static
test fails on any `.or()`, `.filter()` or `.not()` built from a template
literal or string concatenation.

**Tests:**
- unit: policies, hashed keys, fail-closed vs fail-open, last-hop IP, messages,
  429 + Retry-After; filter builders and the search schema; the Admin Center
  action (bounds, AAL2, permission, upsert, audit);
- static: every exported Server Action calls a limiter, every route handler
  calls `limitApi()` (health excepted), no raw PostgREST filters;
- integration, against Supabase local:
  - `rate_limit_consume` as `prisma_app`, window reset and tenant overrides;
  - the function cannot be called from the Data API, anonymous or signed in;
  - RLS and bounds of `tenant_rate_limits`;
  - the real `signIn` and `verifyMfa` against Supabase Auth: the sixth
    attempt is refused even with the right password or code, one IP is limited
    across accounts, login fails closed when the limiter is unreachable, and
    the login is audited on the server;
  - the fourth tenant creation in an hour is refused;
  - `"a,id.eq.1)("` returns no row and no error, where the old filter ran the
    injected `id.eq.1`.

**Accepted for now:**
- The Supabase Auth API stays public (the browser client needs it), so a
  client calling it directly with the anon key skips the app's limiter. Only
  the native per-IP limits protect that path, and they act only on the hosted
  project. The Auth hooks that would close it (password and MFA verification
  attempts) need a paid plan, so they are not used (Principle 8).
- Since login and MFA run on the server, hosted Supabase Auth would count every
  attempt against the server's IP. Phase 23 must forward the client IP with
  `Sb-Forwarded-For` (secret API key, `security_sb_forwarded_for_enabled`),
  or all users share one bucket.
- Without a proxy, `X-Forwarded-For` comes from the client, so the per-IP
  bucket is a first barrier only. The account bucket is not affected.
- The account bucket lets an attacker block a victim's login while they keep
  sending wrong passwords; the victim can sign in again one window (60 s) after
  the attacker stops.
- Fixed windows allow up to twice the limit across a window boundary.
- There is no password-reset flow yet (it arrives with Resend in Phase 23). When
  it is built, its Server Action is caught by the coverage test until it spends

## D29 — Content-Security-Policy with Nonces

**Decision:** the middleware sends a Content-Security-Policy with a fresh nonce
on every response it handles. Scripts run only with that nonce, with no
`'unsafe-inline'` and no `'unsafe-eval'` outside `next dev`. The browser build
ships no source maps. Phase 9b, PR 4.

- `lib/security/csp.ts` builds the policy. Scripts get `'self' 'nonce-<n>'
  'strict-dynamic'`: a nonced script may load the chunks it imports, and
  nothing else runs. `next dev` adds `'unsafe-eval'`, which React's
  development build needs. The other directives are the ones `next.config.ts`
  used to send.
- `src/middleware.ts` makes a 128-bit nonce per request (Web Crypto, Edge
  runtime). It sets the policy on the request, where Next.js reads the nonce to
  put on its own scripts, and on the response, where the browser enforces it.
  It also forwards the nonce as `x-nonce`, replacing any value the client sent.
- `next.config.ts` no longer sends a CSP. Two policies would both apply, and
  one without the nonce would block every script. The other security headers
  stay there.
- The root layout calls `connection()`, so every page renders per request. A
  page prerendered at build time would carry no nonce and break. The build
  lists every route as dynamic.
- `productionBrowserSourceMaps: false` is explicit; the build check of D32
  fails if a `.map` file appears in `.next/static`.

**Tests:**
- unit tests for the policy (no `'unsafe-inline'`, `'unsafe-eval'` only in
  dev, fresh nonces) and for the middleware (same nonce in the header and
  forwarded to the page, a new one per request, set on redirects too);
- `scripts/check-csp.mjs`: CI asks the running web image for `/login` and fails
  unless the policy has a nonce and every `<script>` carries it;
- in the production image, a browser visited 11 pages (login, the employee
  modules, performance forms, MFA and Admin Center) with no CSP violation. An
  inline script injected into the HTML was blocked, and `eval()` threw
  `EvalError`.

**Accepted for now:**
- Styles keep `'unsafe-inline'`: React and Next.js write inline style
  attributes, and a nonce does not cover attributes.
- Files outside the middleware (static assets, `/api/health`) carry no CSP;
  none of them is HTML.
- Rendering every page per request rules out static pages; all of them already
  depend on the session.

## D30 — Server-Only Modules and the Client Boundary

**Decision:** every module that holds a key or a privileged connection starts
with `import "server-only"`. A client component that imports one, directly or
through other modules, fails the build, and a lint rule of our own reports it
first, with the chain of imports. Phase 9b, PR 4.

- **Marked:** `lib/db/admin-client.ts` (superuser), `lib/db/tenant-client.ts`
  (`prisma_app`), `lib/email/index.ts` (`email_enqueuer`) and
  `lib/lms/moodle-client.ts` (`MOODLE_WS_TOKEN`). Its runtime `window` check is
  replaced by the marker. Everything that uses them (`can()`, the rate limiter,
  the LMS sync…) is covered through them.
- **Lint:** `eslint-rules/no-server-only-in-client.mjs`
  (`scalia/no-server-only-in-client`):
  - it applies to files that start with `"use client"`;
  - it follows local imports (`@/…` and relative, not `import type`) until it
    finds the marker;
  - it stops at `"use server"` files, because a client only gets a reference
    to a Server Action;
  - it also refuses `server-only`, `@prisma/client`, `pg` and `pg-boss`
    imported directly.
- **Tests:** Vitest resolves `server-only` to the package's own server build
  (empty), the same thing the `react-server` condition does in Next.js. The web
  and worker configs both do this, since the worker suite imports `lib/email`.

**Tests:** the rule against a fixture tree:
- a direct import, a chain of two files, packages, dynamic imports and
  re-exports are refused;
- Server Action files, type-only imports, plain modules and server components
  pass.

## D33 — Dependabot and Secret Scanning

**Decision:** Dependabot opens dependency updates, CI scans the whole git
history for secrets on every PR, and the CI token can only read the
repository. All of it is free: Dependabot comes with GitHub, and gitleaks is
MIT (Principle 8). Phase 9b, PR 4.

- **Dependabot (`.github/dependabot.yml`):**
  - weekly, Monday;
  - npm from the root lockfile, which covers every workspace, with minor and
    patch updates grouped;
  - GitHub Actions grouped, in `directories: ["/", "/.github/actions/*"]`. The
    docs say `/` covers `.github/workflows` and a root `action.yml` only, and
    that `directories` accepts globs, so the glob adds the local composite
    actions (`supabase-images` uses `actions/cache`). The file passes the
    SchemaStore schema for Dependabot v2;
  - at most one open PR per ecosystem (`open-pull-requests-limit: 1`). They
    are merged between loops, never while a loop PR is open (CLAUDE.md,
    "Forma de trabajo");
  - `pg-boss` is ignored: migration D17 creates its schema for this exact
    version, so an upgrade needs a new migration.
  - `react-native`, `react-native-*`, `expo` and `expo-*` are ignored. Their
    versions are set by the Expo SDK (`apps/mobile`, SDK 52) and move with
    `npx expo install --fix` when the SDK changes, never by Dependabot.
    Dependabot once proposed `react-native` 0.77 → 0.88 inside the
    minor-and-patch group: 0.88 needs React 19.3 (`apps/mobile` has 18.3.1)
    and is outside SDK 52, and CI does not build the mobile app, so it would
    have passed green.
  - Its PRs run the same CI as any other.
- **CI token:** `ci.yml` sets `permissions: contents: read` for `GITHUB_TOKEN`
  at the workflow root. No job needs more: checkout only reads, and the caches
  use the runner's own token.
- **Secret scan:** job "Secret scan" in `ci.yml` runs gitleaks v8.30.1, pinned
  by image digest, over the full history (`fetch-depth: 0`, since a secret
  removed later is still leaked).
  - Its checkout uses `persist-credentials: false`: the gitleaks container
    mounts the checkout, `.git/config` included, and must not see the token.
  - `.gitleaks.toml` keeps the default rules and allows only Supabase local's
    public demo JWTs (issuer `supabase-demo`, the same in every local stack).
  - `npm run check:secrets` runs the same scan locally.
  - The current history (177 commits) is clean. Planted test strings are
    reported: a JWT with a real issuer and a GitHub token.

**Accepted for now:**
- Dependabot does not update the Node base image: the Dockerfiles take it as
  an `ARG` (D17), and `.nvmrc` pins Node. It does not update the gitleaks
  digest or `SUPABASE_CLI_VERSION` in `ci.yml` either. Those move by hand.
- GitHub's own secret scanning and push protection are repository settings,
  outside this repo; turning them on is the owner's call.
- Ignoring `pg-boss` also silences its security updates. It is checked by hand
  with `npm audit` in every phase. The same holds for the Expo-controlled
  packages.

## D34 — Middleware Session Check Without a Call to Auth

**Decision:** the middleware validates the session with
`supabase.auth.getClaims()` instead of `getUser()`. Phase 9b, PR 5.

- `getClaims()` checks the JWT's signature against Supabase Auth's public keys
  (ES256, fetched once and cached). It also refreshes an expired session, so
  the cookie still carries the latest JWT from `custom_access_token_hook`. With
  a symmetric key it falls back to `getUser()` by itself.
- `getUser()` asked Auth on every request. Under load that call was the
  busiest service (up to 3.5 cores in the baseline run).
- What changes: a session revoked in Auth keeps passing the middleware until
  its JWT expires (`jwt_expiry` 900 s). That was already the case for every
  direct call to the Data API, which only checks the JWT, and the pages already
  read claims with `getClaims()`.
- **Accepted for now.** Offboarding (Phase 14, roadmap) must cut access at
  once: a per-user revocation mark read in the middleware (cacheable like
  D35) or a shorter `jwt_expiry`, with a test that a terminated user gets a
  401 or a redirect on the next request.
- The middleware no longer reads the claims twice: one `getClaims()` serves the
  session check, the tenant id header (D27), the tenant check (D21) and the MFA
  step.

## D35 — Caching per Tenant and per Request

**Decision:** what every page repeats is read once. A few things are cached
across requests, always keyed by the tenant of the verified token; the rest is
cached only within one request. Phase 9b, PR 5.

**Across requests:**
- **Tenant check of the middleware (D21).** `lib/tenant/access-cache.ts`
  remembers an allowed (requested tenant, token tenant) pair for 5 s.
  - Refusals and failed lookups are never cached.
  - A tenant suspended in the database is refused at most 5 s later; its new
    tokens already leave it out (hook, D21).
  - The cache has an `invalidate(tenantId)` meant for the suspension path.
    Today suspension is done by the platform in SQL, and the cache lives in
    each process, so the 5 s TTL is the bound. A shared store (Redis, Phase 23)
    would implement the same interface and make invalidation reach every
    instance.
  - **Pending for Phase 12:** nothing calls `invalidate` yet. The platform
    console calls `tenantAccessCache().invalidate(tenantId)` when it suspends
    a tenant (roadmap, Phase 12).
- **Module flags.** `getModuleFlags` uses `unstable_cache` per tenant (tag
  `tenant:<id>:modules`, 60 s).
  - It reads through `public.tenant_module_flags(uuid)`, a SECURITY DEFINER
    function only `prisma_app` can execute, which returns the 12 flags of one
    tenant. The cache is filled outside the request, so it cannot use the
    user's session.
  - Callers pass the tenant id of the verified token.
  - **Pending for Phase 12:** nothing invalidates the flags yet. The platform
    console calls `revalidateTag(moduleFlagsTag(tenantId))` when it turns a
    module on or off (roadmap, Phase 12). Until then a module turned off stays
    visible for up to 60 s.
- **RBP stays out of any cross-request cache.** D14 and the roadmap require
  that a revoked permission stops working at once. That needs an invalidation
  this design does not have, so the permission context is still read on every
  request.

**Within one request (React `cache()`):**
- `getClaims()`, the server Supabase client (`createClient()`) and the current
  employee row (`getCurrentUser()`). The layout and the page used to read the
  employee row and the module flags twice each.
- The permission context of `can()` (D14) is now one batch transaction of two
  statements: the RLS context with `set_config('role', …)` and one query that
  returns flags, grants and permissions. The interactive transaction it
  replaced had six statements. Under load the interactive version ran out of
  pooled connections (`P2028`, "Unable to start a transaction"). Since D47 it
  is a single statement, `SELECT rbp_context(…)`, with no transaction.

**Tests:**
- unit: cache TTL, keys and invalidation; the middleware remembers an allowed
  tenant but not a refusal; `getClaims()` instead of `getUser()`; one
  transaction for six `can()` calls;
- integration: `tenant_module_flags()` for `prisma_app` only, the same flags
  as the table, no row for an unknown tenant, refused from the Data API.

## D40 — Design Tokens and Theme Base

**Decision:** every color, radius, shadow, font and duration the web app uses
is a semantic token. A preset is data: one file of values per preset, rendered
to CSS variables on the server. Tailwind 4 reads the tokens through `@theme`,
and its default palette is removed, so a component cannot use a literal color.
Phase 9c, PR 1 (D18, D19).

**Three layers:**

1. **Preset values** (`src/lib/theme/presets/clean.ts`): a typed object with
   the light and dark color sets and the shape values (radii, shadows). The
   five presets of Phase 11 (Glass, Soft, Midnight, Editorial, Bento) are five
   more files of the same type. The high-contrast variant is derived from the
   preset (D18 calls it automatic); a preset may override single values.
2. **Theme CSS** (`themeCss(preset)` in `src/lib/theme/`): renders the
   `--theme-*` variables for each mode and contrast, and validates every value
   against a strict format (hex colors, lengths, shadow lists) before it
   reaches CSS. A theme is never a stylesheet (D18), so tenant values in
   Phase 11 go through the same check. The root layout puts it in a `<style>`.
3. **Tailwind contract** (`src/app/globals.css`): `@theme inline` maps each
   utility token to its `--theme-*` variable, and `--color-*: initial` drops
   the default palette. `bg-slate-800` generates no CSS; `bg-surface` does.

**Color tokens.** All are opaque except `overlay`, so every pair has one
contrast ratio to test.

| Group | Tokens (utility) | Role |
|---|---|---|
| Surfaces | `canvas`, `surface`, `surface-muted`, `surface-raised`, `surface-hover`, `surface-strong`, `overlay`, `qr-surface` | Page, cards, subtle sections, inputs and chips, hover, neutral fills (progress tracks), modal backdrop, the light background a QR code needs |
| Text | `fg`, `fg-muted`, `fg-subtle` | Primary, secondary and tertiary text (placeholders included) |
| Lines | `line`, `control` | Decorative dividers and outlines; the boundary of form controls |
| Focus | `focus` | Focus indicator |
| Accent | `accent`, `accent-hover`, `accent-fg`, `accent-subtle`, `accent-line`, `on-accent` | Primary action and active state, its hover, accent text and links, selected background, tinted border, text on the accent |
| States | `success`, `warning`, `danger`, `info`, each with `-hover`, `-fg`, `-subtle`, `-line` and `on-` | The same five roles as the accent, per state |
| Categories | `category-1` … `category-3`, each with `-fg`, `-subtle`, `-line` | Labels that tell categories apart (skill types, ARCO request types) and carry no state |

**Contrast rules**, tested for every pair in light, dark, high-contrast light
and high-contrast dark:
- 4.5:1 for text: `fg`, `fg-muted`, `fg-subtle` and every `-fg` token on every
  surface they are used on; each `-fg` on its `-subtle`; each `on-` on its
  solid color and its hover.
- 3:1 for components: `control` and `focus` against the surfaces; `accent`,
  the states and `surface-strong` as indicators (progress bars, active tabs,
  status dots) against the surfaces. Indicators rest on `canvas`, `surface`,
  `surface-muted` and `surface-raised`; `surface-hover` is transient and only
  carries text, which is tested on it.
- High contrast raises text to 7:1 and boundaries to 4.5:1. The derivation
  (`deriveHighContrast()`) removes the tints (every `-subtle` becomes the
  plain surface), makes muted and subtle text equal to `fg`, turns tinted
  borders into their text color, and gives each solid fill black or white text
  at 7:1. `ensureContrast()` does the adjusting; Phase 11 uses it for tenant
  brand colors.

**Other tokens:**
- Radii: `--radius-xs` … `--radius-2xl` and `full`. Clean keeps Tailwind's
  values.
- Shadows: `--shadow-2xs` … `--shadow-2xl`, per mode (Tailwind's values in light, darker in dark).
- Spacing: Tailwind's 4 px step (`--spacing: 0.25rem`), plus the form spacing
  of D19 as `form-label` (8 px), `form-help` (4 px), `form-field` (20 px) and
  `form-section` (24 px).
- Typography: `--font-sans` is Inter, self-hosted with `next/font/local` (SIL
  Open Font License 1.1, license file next to the font); `--font-mono` is the
  system monospace stack. The type scale is Tailwind's.
- Motion: `--motion-fast`, `--motion-base`, `--motion-slow` and
  `--ease-standard`; under `prefers-reduced-motion: reduce` every duration is
  0.

**Theme selection, on `<html>`:**
- `data-preset="clean"`.
- `data-theme="system" | "light" | "dark"`, default `system` (follows
  `prefers-color-scheme`).
- `data-contrast="auto" | "more"`, default `auto` (follows
  `prefers-contrast: more`).
- `system` and `auto` are resolved by CSS media queries, so with nothing
  stored the page is right on first paint without any script. A stored choice
  (light, dark or more contrast) is applied by an inline script in `<head>`
  before the first paint. That script carries the request's CSP nonce (D29),
  accepts only the listed values and changes nothing else.

**Components** use only these tokens. A static test fails on Tailwind palette
classes, arbitrary color values, hex colors and opacity modifiers on colors
(a translucent token has no fixed contrast), and on a solid accent or state
background whose text is not its `on-` token.

**Fonts and CSP:** the CSP no longer lists `fonts.googleapis.com` or
`fonts.gstatic.com`; fonts and styles come from `'self'` only, and
`scripts/check-csp.mjs` fails if an external origin appears in `font-src` or
`style-src`.

**Implementation (PR 1 of Phase 9c):**
- `src/lib/theme/`: `tokens.ts` (names and types), `presets/clean.ts` (the
  values), `contrast.ts` (WCAG ratio, pairs, `ensureContrast()`),
  `high-contrast.ts`, `css.ts` (`themeCss()`), `boot-script.ts` and `index.ts`
  (the CSS and attributes the app renders today).
- `src/app/layout.tsx` renders `data-preset`, `data-theme` and `data-contrast`
  on `<html>`, the boot script with the nonce and the theme `<style>`.
  `global-error.tsx` renders its own `<html>` with the same tokens.
- `src/fonts/inter/`: Inter variable, latin subset (U+0000–00FF, which covers
  Spanish), from `@fontsource-variable/inter` 5.3.0, with `OFL.txt` and its
  SHA-256 in a README.
- Migration: 883 palette classes in 30 files, plus the two hex colors of

  the local components declared in those files.

- The branches of a conditional (`a ? X : Y`), and sibling `&&` blocks that

  branch, not the sum.

## D44 — Accessibility in CI: axe, e2e and Closing Screenshots

**Decision:** the Playwright suite of `apps/web` runs real flows against the
production image of the local stack, in the Docker job of CI after
`npm run local:up`, with axe on every existing screen in light and dark, the
zoom checks of WCAG 1.4.4 and 1.4.10, and the closing screenshots at 360, 768
and 1280 px. Phase 9c, PR 5. The goal is WCAG 2.2 AA.

**axe policy:**
- A scan fails on any violation of a rule tagged `wcag2a`, `wcag2aa`,
  `wcag21a`, `wcag21aa` or `wcag22aa`. Rules tagged `best-practice` run too;
  their findings are listed in the report and do not fail.
- No rule is disabled and nothing is excluded from a scan. If an exclusion
  ever becomes unavoidable, it goes in this section with its reason, the exact
  selector and the phase that removes it. Today there is none.
- The report keeps each rule, its impact, the CSS selectors of the nodes and
  axe's failure summary; never a node's HTML or text, which can carry what is
  on screen.
- Before a scan the test waits for the theme's color transitions (D40) to end
  and for the page's `<title>`: Next.js streams the metadata of a dynamic page,
  so after a client-side navigation the title arrives a moment after the
  content. A page that never gets a title still fails, by timeout.

## D45 — A Failed Query Is Not "No Data"

**Decision:** extends D27. A Supabase query that fails is never shown as an
empty result. The section it feeds shows the error (generic text and request
id, through `safeError()`), or the whole page does when it is the page's main
query. A static test with the TypeScript parser fails when a query's `error`
is not read, in pages, layouts, Server Actions, HTTP routes and the libraries
they call. Correction PR between PR 5 and PR 6 of Phase 9c.

**The bug that started it:**
- The employee detail showed "Sin información laboral registrada" to
  everyone, the admin included (found by the D44 screenshots).
- Its job query embedded `business_units(name)` and `legal_entities(name)` in
  `ec_job_information`, which has no foreign key to either table. PostgREST
  answered PGRST200, `data` was null, and the page read only `data`.
- A failed PostgREST query resolves with `{ data: null, error }`; it does not
  throw. Reading only `data` turns every failure into an empty state. The same
  pattern was in about 70 places.

**Business unit and legal entity:**
- They come from the department of each job record:
  `departments(name, business_units(name), legal_entities(name))`
  (`lib/employees/job-information.ts`, `JOB_INFORMATION_SELECT` and
  `jobOrganization()`), for the current record and the history. No migration.
- The department's own business unit and legal entity are read, so the
  history shows today's values of a past record's department. Whether the two
  fields move into the job record, as in SuccessFactors, is decided in Phase 14
  (ROADMAP).

**The rule (`lib/errors/query-error.ts`, `components/ui/load-error.tsx`):**
- A page with independent queries shows the error per section; the other
  sections still render. `queryErrorMessage(event, error)` returns the
  message, or null; `firstError()` picks the first error of the queries that
  feed one section; `LoadError` shows it with `role="alert"`.
- The whole page goes to error (`PageLoadError`: the page's heading and the
  message) only when its main query fails: the record of the employee detail,
  the own profile on Mi perfil and the dashboard, the employees list, the
  positions of the org chart and the ARCO requests.
- Counts and headings that depend on a failed list do not claim zero: the
  roles, groups, goals and feedback headings drop their count, the stats that
  come from a failed list are not shown, and the employee header does not say
  "Sin puesto" when the job query failed.
- Per page:
  - Employee detail: page error for the employee; sections for personal
    data, job (current, history and manager) and compensation.
  - Employees list: page error for the list and for the direct reports,
    without which the list cannot tell which rows open a profile.
  - Dashboard: page error for the profile; sections for the tenant KPIs and
    the goals.
  - Mi perfil: page error for the profile; the manager is a field of the
    personal data section; feedback is its own section.
  - Desempeño: goals and feedback per tab; the stats come from the goals.
  - Habilidades: radar (position, classification, required skills, own
    skills), catalog (ontology, own skills) and team (direct reports, their
    names and skills) per tab, with their stats.
  - Administración: stats, system configuration, audit log and rate limits
    per block. The rate limits show no defaults when the tenant's own values
    cannot be read: the admin would save over them.
  - Gestión de roles: roles and groups per list.
  - Organigrama and Derechos ARCO: page error.

**`maybeSingle()` only where "no record" is a business case.** `.single()`
answers an error (PGRST116) when there is no row; that error was being read as
"no row" by code that ignored it. Every query that changed:
- `getCurrentUser()`: an account without an employee row (D35, null).
- Employee detail: the employee (no row is a 404: it does not exist or RLS
  hides it); the current personal, job and compensation records (an employee
  may have none yet); the manager (out of the caller's RLS view, shown "—").
- Dashboard and Mi perfil: the profile (no employee row says so); the manager
  on Mi perfil (out of view, "Sin jefe").
- Habilidades: the position and its job classification (none, or not
  readable, means no required skills).
- "Tomar Acción": the employee's name (not visible is "not found").
- Server Actions: the employee row of the actor in the employee actions; the
  ARCO request being processed and the skill being updated ("not found"); the
  membership in `switchTenant` (a refusal) and the settings row in
  `revokeMembership` (a person may have none).
- LMS: the tenant's map in `/lms/launch` and `provisionTenantLms()` (not yet
  provisioned), in `syncLmsUsers()` (not provisioned) and the user's map in
  `getEmployeeCompletions()` (no Moodle account, no completions).
- `.single()` stays after an insert that returns the new row, where a missing
  row is an error.

**The current user (`lib/auth/current-user.ts`):**
- A failed read throws `CurrentUserUnavailable`, which carries safeError()'s
  message; null still means no employee row.
- The protected layout catches it and renders a shell without menu or page:
  the header with "Cerrar sesión", "Algo salió mal" and the message with the
  request id. The person is not sent to the login as if there were no
  session. The Admin Center layout renders nothing in that case (the
  protected layout already shows it).
- Next.js renders the page in parallel with the layout; the page gets the
  same cached rejection and rethrows it. The user never sees it (the layout
  does not render the page), and `onRequestError` skips
  `CurrentUserUnavailable`, already logged by safeError() as
  `auth.current_user` with the same request id.
- Server Actions use `currentUserOrError()`, which returns the message
  instead of throwing: performance, Administración, ARCO and skills actions
  return it; the MFA and login audit helpers skip the audit (the read failure
  is already logged). `/api/colleagues` answers 500 "unavailable", not 401.

**"Tomar Acción":**
- Its six lists were read from the browser with the anon client, and a failed

  `limitRead()` (a token of the api bucket, so reads do not spend the person's

**Routes and libraries:**

**Static test (`__tests__/static/query-errors.ts` and `.test.ts`):**
- A query is a call chain that starts at `.from()` or `.rpc()` (not
  `Array.from`). It is checked where it is awaited: directly, through a

- The result must be bound with `error` (or to a name whose `.error` is read)

- It runs over every file in `src`, and checks that pages, layouts, Server
  Actions and routes are among them. Negative controls give one reason each

  pattern the code uses.

## D46 — No Hard Delete from the Data API; Ids Validated with `z.guid()`

**Decision:** anon and authenticated cannot delete rows anywhere in `public`:
no DELETE privilege, no PERMISSIVE DELETE policy and no default privilege that
would give it to a new relation. Every id in Server Actions and routes is
validated with `z.guid()`, which accepts the seed's ids. Security PR between
PR 5 and PR 6 of Phase 9c, from the findings of D45; the read side (RLS by RBP
population) is D47.

**What was there (`supabase/migrations/20261109010000_d46_no_hard_delete.sql`):**
- Fifteen PERMISSIVE DELETE policies from the first migrations allowed a delete
  inside the caller's tenant, for the role `public` (anon and authenticated):
  `business_rules`, `continuous_feedbacks`, `departments`,
  `job_classifications`, `job_families`, `job_informations`, `job_roles`,
  `object_definitions`, `performance_goals`, `positions`,
  `succession_nominees`, `succession_plans`, `talent_pool_entries`,
  `talent_pools` and `users`.
- Each was neutralized by a RESTRICTIVE `no_hard_delete_authenticated`
  policy (`USING false`), and anon has no tenant, so nothing could be deleted.
  But dropping one RESTRICTIVE policy would have opened its table.
- Supabase's default grants gave DELETE to anon and authenticated on 36 of the
  39 tables, and the default privileges of `postgres` in `public` kept giving
  it to every new table (D25 removed TRUNCATE, TRIGGER, REFERENCES and
  MAINTAIN, not DELETE).
- No screen deletes: there is no `.delete()` of Supabase or Prisma in the app,
  the worker or the packages. Only the operator scripts delete
  (`restore-tenant`, `e2e-accounts`), connected as `postgres`. The two SQL
  functions that delete (`rate_limit_consume`, `purge_expired_rate_limits`)
  are SECURITY DEFINER, and neither anon nor authenticated may execute them.
  Nothing had to move to soft delete.

**The change:**
- The fifteen PERMISSIVE policies are dropped. The RESTRICTIVE `false` ones
  stay as a second lock: they can only take rows away.
- `REVOKE DELETE ON ALL TABLES IN SCHEMA public FROM anon, authenticated`
  (tables, partitioned tables, views, materialized views and foreign tables),
  and the same on the default privileges of `postgres` in `public`.
- `supabase_admin`'s own default privileges still grant DELETE. They apply only

## D47 — Reads by RBP Population

**Decision:** personal, job, pay, talent and RBP data are read through the
same rule as `can()`: one's own rows, plus the population the role grants
give for the permission that guards the data (D14). Holding an
`is_admin_role` role, or the `owner` app_role, no longer opens them. Second
security PR between PR 5 and PR 6 of Phase 9c, after D46.

**What was there:**
- `ec_job_information`, `group_members`, `role_grants` and `lms_user_map`:
  readable by the whole tenant. Anyone could read every job record (title,
  manager, department), who sits in which group and which roles each group
  holds, so who the administrators are.
- `ec_compensation`, `ec_personal_information` and `employee_skills`: own,
  any `is_tenant_admin()` (any `is_admin_role` grant, whatever its keys) or the
  manager of the current job record.
- `performance_goals`, `continuous_feedbacks` (author or subject),
  `arco_requests` (subject) and `audit_logs`: own or any `is_tenant_admin()`;
  an admin read PRIVATE feedback too.
- `users`: every column, `performance_score` and `potential_score` included,
  for the whole tenant.
- `job_informations`, `succession_nominees` and `talent_pool_entries`:
  readable by the tenant, with no screen.

**The rule (`supabase/migrations/20261110010000_d47_rbp_reads.sql`):**
- The population is defined once, in `rbp_population_user_ids(tenant, user,
  population)`: `all` is the tenant, `self` the user, `direct_reports` whoever
  has the user as manager in their current job record (as `can()` read it),
  `same_department` whoever shares the user's non-null department.
  These are two sources: `same_department` reads `users.department_id`,
  while `direct_reports` (and the department the directory and the employee
  detail show) come from the current job record. Phase 14 makes one source of
  truth for the department.
  `rbp_user_ids()` is the union of the populations of the user's grants of
  roles holding the key and action, if the key's module is active
  (`rbp_module_active()`, the same flags as `PERMISSION_MODULE_MAP`). These
  three are internal: no role of the app may execute them.
- The policies call `rbp_visible_user_ids(key, action)` and
  `rbp_has_permission(key, action)`, which answer for whoever runs the query
  (`current_app_user_id()`, `requesting_tenant_id()`). Both are SECURITY
  DEFINER, STABLE, with an empty `search_path`, executable by authenticated.
- `can()` stops reading `role_grants` and `group_members` as authenticated
  (those are now limited to one's own rows). It loads its context with
  `rbp_context(tenant, user)` and checks `direct_reports` and
  `same_department` with `rbp_target_in_population()`, which only `prisma_app`
  may execute (the D42 pattern), so `can()` answers for any user and does not
  depend on the policies it is compared with. `withTenant()` had no other
  caller and is gone.
- `can()` now evaluates the union of the populations that grant a key. Before,
  the first `direct_reports` or `same_department` grant decided alone: a
  manager who was also an HR administrator (`all`) could be refused depending
  on the order of the grants. Unit test in `can.test.ts`.

| Data | Readable by |
|---|---|
| `ec_compensation` | own + `ec.view_compensation` (new key) |
| `ec_personal_information`, `ec_job_information` | own + `ec.view_team_profiles` + `ec.manage_employees` |
| `employee_skills` | own + `tih.employee_skills` |
| `performance_goals` | own + `pmgm.manage_team_goals` (edit) + `pmgm.manage_goal_plans` (edit) |
| `continuous_feedbacks` | author, subject, and the population of `pmgm.view_team_feedback` for the subject unless PRIVATE |
| `arco_requests` | subject + whoever holds `arco.manage` |
| `audit_logs` | whoever holds `admin.view_audit_logs` |
| `group_members`, `lms_user_map` | own + whoever holds `admin.manage_roles` (edit) |
| `role_grants` | the grants of one's own groups + `admin.manage_roles` (edit) |
| `users.performance_score`, `potential_score` | own + `ec.manage_employees`, through `talent_scores()` |
| `job_informations`, `succession_nominees`, `talent_pool_entries` | nobody (RESTRICTIVE `false`) until they have a screen (Phase 18a) |

- `ec_job_information` keeps its tenant policy and gets a RESTRICTIVE one with
  the rule; the other tables had a single SELECT policy, which is altered.
- **Directory:** the employee list showed the title and department of every
  listed person from their job record. It now calls `directory_entries(ids)`
  (SECURITY DEFINER, STABLE, empty `search_path`, filtered by
  `requesting_tenant_id()`): first name, last name, current title and current
  department, nothing else, and only with `ec.view_org_chart`; without it the
  call fails with 42501 rather than answering an empty directory. The org
  chart reads positions, not job records, and did not change.
- **Scores:** `REVOKE SELECT ON users` and `GRANT SELECT (every other column)`
  to anon, authenticated and `prisma_app`. `prisma_app` had its own SELECT on
  the whole table (`app_roles`), so Prisma would still have read every score
  of the tenant. The list of columns is explicit: a column added to `users`
  later is unreadable by anon, authenticated and `prisma_app` until a
  migration grants it (a rule of `CLAUDE.md`). `talent_scores(ids)` answers own scores and those of the population
  of `ec.manage_employees` until Phase 18a gives them a key. The dashboard and
  the profile read their own through it, and every `select` on `users` names
  its columns.
- **`ec.view_compensation`:** the compensation section of the employee detail
  had no key of its own ("admin or team"). It now asks `can()` for
  `ec.view_compensation` on the employee. Owner and HR Administrator get it
  with `all` and Manager with `direct_reports`, in the seed, in the tenant
  sign-up (`create-tenant.ts`) and, for tenants that exist, in the migration.
- **Writes do not change.** They still go through `insert_effective_record`
  (by `app_role`) and the existing write policies: Known Risk below, Phase 11.

**Behavior that changes:**
- An administrator whose roles lack a data key sees only their own rows of it
  (an `is_admin_role` role with only `admin_center.access` reads no one
  else's job, pay, skills, goals, feedback, ARCO requests or audit log).
- HR Administrator and Owner hold no `pmgm.view_team_feedback` in the seed, so
  they no longer read other people's feedback. PRIVATE feedback is only for
  its author and its subject. Decision (least privilege): they stay without
  it. Once Admin Center edits RBP (Phase 11), each tenant decides whether to
  grant it; Phase 19 (CPM) defines who in HR reads non-private feedback.
- Managers now read the goals (`pmgm.manage_team_goals`) and the non-private
  feedback (`pmgm.view_team_feedback`) of their direct reports, which their
  role already granted and the policies did not allow.
- `syncLmsUsers()` and `getEmployeeCompletions()` read `lms_user_map` with the
  session's client. Nothing in the app calls them yet; when something does,
  the caller needs `admin.manage_roles` (or the worker, D17).
- With `all`, `can()` does not check that the target belongs to the tenant; RLS
  does, and the comparison test covers it with an employee of another tenant.

**Tests:**

## Known Risk — `insert_effective_record` Authorizes by `app_role`, Not RBP

**Status:** Accepted (temporary). Registered 2026-11-02.

**Affected component:** `insert_effective_record()` (SECURITY DEFINER RPC in
`supabase/migrations/`).

**Current state:** The function checks `has_app_role('owner') OR
has_app_role('hr_admin')` to authorize the caller. This reads the `app_role`
string from `user_tenant_memberships` (baked into the JWT at login). It does
**not** check RBP permissions (`role_grants` → `role_permissions`).

**Reads are not affected:** since D47 the policies that limit reads follow
RBP populations; this risk is about writes only.

**Risk:** When Admin Center (Phase 11) enables custom roles with
`ec.manage_employees`, a user granted that RBP permission but without the
`owner` or `hr_admin` app_role will be rejected by the function. Conversely,
a user with the `hr_admin` app_role whose RBP permissions have been narrowed
will still pass. The function's authorization does not follow the RBP model.

**Planned fix (Phase 11 — Admin Center with custom roles):**

1. Replace the `has_app_role()` checks in `insert_effective_record()` with an
   RBP permission check (either calling the planned `can()` SECURITY DEFINER
   function or querying `role_grants`/`role_permissions` directly).
2. Apply the same change to any other database function that currently
   authorizes by `app_role` instead of RBP.
3. Add integration tests verifying that a custom role with `ec.manage_employees`
   can call the function, and that a role without it is rejected.

## Known Risk — Login Audit Depends on the Client

**Status:** Partially resolved by D28 (2026-11-05). Login and MFA verification
now run in Server Actions: `AUTH_LOGIN`, `MFA_VERIFY` and `MFA_VERIFY_FAILED`
are written by the server, and a failed login writes an `auth.login_failed`
JSON line (D27). Gap 1 remains for the audit table: a failed login has no
tenant or actor, so it is a log line, not an audit entry. Gap 2 remains: direct
calls to the Supabase Auth API leave no app audit. MFA enrollment still runs in
the browser. The original analysis follows.

**Status at registration:** Accepted (temporary). Registered 2026-11-03.

**Affected component:** Login page (`apps/web/src/app/login/page.tsx`),
MFA pages (`apps/web/src/app/(protected)/mfa/enroll/page.tsx`,
`apps/web/src/app/(protected)/mfa/verify/page.tsx`) and their Server Actions
(`apps/web/src/app/login/actions.ts`, `apps/web/src/app/(protected)/mfa/actions.ts`).

**Current state:** `signInWithPassword` and the MFA `challenge`/`verify` calls
run in the browser. After each operation, the client calls a Server Action
(`logLoginEvent`, `logMfaEnroll`, `logMfaVerify`, `logMfaEnrollFailed`,
`logMfaVerifyFailed`) which writes the audit entry. This has three gaps:

1. **Failed logins are not recorded.** A failed `signInWithPassword` has no JWT
   (no tenant, no user), so `write_audit_log()` cannot identify the actor or
   tenant. No audit trail exists for brute-force attempts.
2. **Direct API calls bypass the audit.** A client that authenticates or
   completes MFA directly against the Supabase Auth API (e.g. via
   `supabase.auth.signInWithPassword` or `supabase.auth.mfa.verify` outside the
   web app) produces a valid session with no audit entry.
3. **MFA failure events depend on the client.** `MFA_ENROLL_FAILED` and
   `MFA_VERIFY_FAILED` are logged only because the browser calls the Server
   Action after receiving an error from `mfa.verify()`. A direct API caller that
   skips the web app leaves no trace of failed MFA attempts.

**Risk:** Compliance frameworks (SOC 2, ISO 27001) typically require logging of
both successful and failed authentication attempts. The current approach leaves
a gap that could mask credential-stuffing and MFA brute-force attacks.

**Test coverage gap:** The integration tests validate that the `write_audit_log`
RPC writes and that RLS returns the entries to admin users, but they do not
verify that the login and MFA pages actually invoke their Server Actions. This
will be covered by a Playwright e2e test when the fix below is implemented.

**Complementary source — `auth.audit_log_entries`:** Supabase's built-in auth
audit log (in the `auth` schema) records every GoTrueAuth event (sign-in,
sign-up, token refresh, MFA challenge) with IP metadata. It could serve as a
cross-reference for events the app misses, but it lives in the `auth` schema
(not accessible via PostgREST/RLS), so reading it requires `service_role` or a
SECURITY DEFINER view, and its retention is controlled by Supabase, not the
application. Useful as a secondary check, not a primary audit trail.

**Planned fix (separate PR, alongside Phase 9b rate-limiting):**

1. Move `signInWithPassword` and MFA `challenge`/`verify` into Server Actions so
   the server controls both the auth call and the audit write. On success, write
   `AUTH_LOGIN` / `MFA_VERIFY` / `MFA_ENROLL`; on failure, write
   `AUTH_LOGIN_FAILED` / `MFA_VERIFY_FAILED` / `MFA_ENROLL_FAILED` to a
   dedicated `auth_events` table using `service_role` from the server, recording
   email (for login) or user id (for MFA), IP and user-agent without requiring
   the client to initiate the audit call.
2. Do not grant `EXECUTE` on `write_audit_log` to `anon`. The `auth_events`
   table uses a separate, tightly-scoped insertion path via `service_role`.
3. Evaluate exposing `auth.audit_log_entries` via a read-only SECURITY DEFINER
   view for admin users, as a complementary data source for forensics.
4. Add Playwright e2e tests that exercise the login and MFA flows end-to-end and
   verify that the expected audit entries appear in the database.

## Known Risk — Supabase CLI Version Pinned in CI

**Status:** Accepted (permanent). Registered 2026-11-03.

**Affected component:** `.github/workflows/ci.yml` — all jobs that use
`supabase/setup-cli@v3`.

**Current state:** The Supabase CLI is pinned at v2.122.1, set once in
`SUPABASE_CLI_VERSION` at the top of `ci.yml` (D26). On 2026-11-03
`version: latest` pulled v3.0.0, which changed how the shadow database
used by `supabase db diff` initializes grants on the `public` schema.
This caused the "DB reset sync test" job to report 7 unexpected GRANT/
REVOKE/COMMENT statements on the public schema that were not in
`supabase/drift-allowlist.txt`.

**Risk:** The pinned version will fall behind. Security patches and new
features in the Supabase CLI will not be picked up automatically.

**Before upgrading the CLI version:**

1. Run `supabase db diff` locally with the new version against a clean
   `db reset` and compare against the drift allowlist.
2. If new public-schema grant statements appear, update either
   `db-reset-sync.sh` Step 2 (the `CREATE SCHEMA public` + GRANTs block)
   or `supabase/drift-allowlist.txt` to match the new shadow DB behavior.
3. Verify all three CI jobs pass before merging the version bump. The
   Supabase image caches are keyed by the CLI version (D26), so the first
   run after a bump pulls the new images and caches them again.
