# Scalia HR — Architecture Decisions

> SaaS B2B HCM multi-tenant, modular clone of SAP SuccessFactors.
> Stack: Next.js 15 (App Router) + Supabase + Prisma (client-only).

---

## D1 — Single Source of Schema

**Decision:** `supabase/migrations/` (raw SQL) is the **only** source of truth
for the database schema. Prisma is used exclusively as a type-generation client
via `npm run db:sync` (`prisma db pull && prisma generate`).

**Rationale:** Supabase RLS policies, custom functions (`requesting_tenant_id`,
`is_tenant_admin`, `custom_access_token_hook`), FORCE ROW LEVEL SECURITY, enum
types, and GRANTs cannot be expressed in Prisma's migration DSL. Maintaining two
migration chains (Prisma + SQL) creates drift and security gaps.

**Rules:**
- `prisma migrate` and `prisma db push` are **prohibited**.
- `prisma/migrations/` directory must not exist.
- `schema.prisma` uses `@@map`/`@map` only as generated by `db pull`.
- Every business table has `tenant_id uuid NOT NULL` with a FK to `tenants(id)`.

---

## D2 — Tenant in the JWT

**Decision:** The active tenant is injected into the Supabase JWT via a
`custom_access_token_hook`. RLS policies read it with
`public.requesting_tenant_id()` (JWT-only, no fallback).

> **S1 change:** `current_tenant_id()` was dropped. All callers now use
> `requesting_tenant_id()`, which reads **only** the JWT claim — no
> `set_config` fallback.

**Tables:**
- `user_tenant_memberships` — maps users to tenants with `app_role` and
  `is_active` flag. Composite PK `(user_id, tenant_id)`.
- `user_settings` — stores `active_tenant_id` per user.

**Hook:** `public.custom_access_token_hook(event jsonb)` (SECURITY DEFINER,
`search_path = ''`) adds `tenant_id` and `app_role` claims from the active
membership. Only `supabase_auth_admin` can execute it.

**Client:**
- `switchTenant(tenantId)` Server Action validates membership (Zod + DB),
  updates `active_tenant_id`, refreshes session.
- `revokeMembership` deactivates the membership and signs out the user globally.

## D3 — Prisma Without RLS Bypass

**Decision:** The Prisma connection uses a custom PostgreSQL role `prisma_app`
with `NOBYPASSRLS`. Every query runs inside a `$transaction` that first sets
`role authenticated` and injects JWT claims via `set_config`.

**Implementation:**
- `lib/db/tenant-client.ts` — sets `request.jwt.claims` per operation.
- `lib/db/admin-client.ts` — privileged connection, importable only from
  `lib/jobs/` and `lib/admin/`.
- ESLint `no-restricted-imports` enforces boundaries.

**Connection URL:** `DATABASE_URL` connects through the Supabase pooler as
`prisma_app.<project-ref>` on port 6543 (transaction mode). The password is
set by the `db-remote-sync` workflow from the `PRISMA_APP_PASSWORD` secret in
the `remote-db` GitHub environment. See `.env.example` for the full URL format.

## D4 — Secrets & Network Hardening

**Rules:**
- All secrets read from `.env` (never committed). `.env.example` has
  placeholders only.
- Docker services publish ports on `127.0.0.1` only.
- `check:forbidden` (`scripts/check-forbidden.sh`, run as `npm run
  check:forbidden`) enforces two categories:
  1. **Old project name** — the pattern is assembled at runtime from string
     fragments so the script never contains the literal name. It searches
     ALL git-tracked file contents and filenames with zero exceptions.
  2. **Secret patterns** — `"service_role"`, `"bitnami"`, `"MOODLE_WS_TOKEN"`
     in client code (`apps/web/src`, `packages`); server-only files that
     legitimately reference them are allowlisted inside the script.
- The check runs in three places: CI (`app` job, before lint), pre-commit
  (husky + lint-staged on `*.{ts,tsx,js,jsx,json,yml,yaml,md,sql,sh,toml}`),
  and a Vitest test (`forbidden-name.test.ts`).

## D5 — LMS Integration (Moodle)

**Decision:** Moodle (`moodlehq/moodle-php-apache`) runs as a sidecar service
alongside the application stack. Scalia HR communicates with it exclusively via
REST web services, using a single service token (`MOODLE_WS_TOKEN`) stored
server-side.

**SSO:** `auth_userkey` plugin, mapping by `username` = Supabase user UUID.
The `/lms/launch` route auto-provisions the Moodle user on first access and
redirects via `auth_userkey_request_login_url`.

**Tenant Isolation:**
- Each tenant gets its own Moodle **category** (courses) and **cohort**
  (employees), stored in `lms_tenant_map`.
- `lms_user_map` associates each Supabase user with their Moodle user ID.
- Both tables have RLS ENABLED + FORCED, scoped by JWT `tenant_id`.

**Sync (`lib/jobs/lms-sync.ts`):**
- ACTIVE + unmapped → create Moodle user, add to cohort, store mapping.
- TERMINATED + mapped → suspend in Moodle.
- `is_anonymized` + mapped → suspend + anonymize (ARCO: firstname=Usuario,
  lastname=Anonimizado, email=`anon_{id}@scalia.local`).
- ACTIVE + mapped → unsuspend (rehire).

**Security:**
- `moodle-client.ts` has a `typeof window !== "undefined"` server-only guard.
- `MOODLE_WS_TOKEN` is in the `check:forbidden` list.
- Server-only files (moodle-client, provision-tenant, lms-sync) are allowlisted.
- Moodle Docker service binds only to `127.0.0.1`.

## D6 — S1 Security Hardening

**Decision:** Harden all SECURITY DEFINER functions, unify tenant resolution,
add RESTRICTIVE RLS policies on PII/compensation tables, rewrite ARCO policies
to role-based access, and consolidate RBP to v2 model.

**Changes (Loop S1):**

1. **`requesting_tenant_id()`** — now the ONLY tenant function. Reads JWT claim
   only, no `set_config` fallback. `current_tenant_id()` dropped.

2. **SECURITY DEFINER functions** — all now have `SET search_path = ''` with
   fully schema-qualified references: `is_tenant_admin`, `insert_effective_record`,
   `effective_record_at`, `anonymize_user`, `export_user_data`.

3. **ARCO policies** — rewritten with `requesting_tenant_id()` + role-based
   access: subject sees own requests (SELECT), admin manages (INSERT/UPDATE).
   `service_role` bypass added.

4. **PII RESTRICTIVE policies** — `ec_personal_information` and `ec_compensation`
   now have RESTRICTIVE SELECT policies: user sees own + direct manager +
   tenant admin. INSERT/UPDATE restricted to admin only.
   Helper functions: `current_app_user_id()`, `has_app_role(text)`.

5. **RBP v2 model** — `can()` and Admin Center UI rewritten to use v2 tables:
   - `role_grants` (with `target_population` enum) replaces `role_assignments`
   - `group_members` replaces `permission_groups.criteria_json` for membership
   - `role_permissions.permission_key/action/field_key` replaces `permission_name`
   - v1 artefacts dropped (`role_assignments` table, `criteria_json` column, `permission_name` column)

6. **CI** — Prisma drift check added to db job. Integration tests moved to
   `__tests__/integration/`. New S1 integration tests (17 cases).
   `mfa-flow.test.ts` verifies TOTP enroll/verify against the local
   Supabase auth server (AAL1→AAL2 promotion, policy guards, invalid code
   rejection). `module-flags.test.ts` verifies flag gating and RLS
   isolation between tenants.

## D7 — Migration Policy & Remote Sync

**Decision:** Changes to the remote Supabase database are applied **only** through
the `db-remote-sync` GitHub Actions workflow, never manually or via the Supabase
MCP `apply_migration` / `execute_sql` tools.

**Workflow:** `.github/workflows/db-remote-sync.yml`
- **Trigger:** `workflow_dispatch` only (manual from GitHub Actions UI).
- **Environment:** `remote-db` (requires approval + secrets).
- **Secrets:** `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_URL`, `SUPABASE_PROJECT_REF`.
- **Modes:**
  - `reset` — pushes all local migrations from scratch (`supabase db push --include-all`).
  - `repair-push` — reverts remote-only migrations, then pushes.
- **Safety:** requires typing `CONFIRM`, creates a schema + data backup uploaded as
  an artifact (retained 30 days), and verifies with `supabase db diff --linked`
  after applying.

**Rules:**
- `supabase/migrations/` on `main` with CI green is the only source that feeds the
  remote database.
- The Supabase MCP server is used in **read-only** mode for the remote project
  (queries, migration list, table inspection). DDL is prohibited via MCP.
- Every sync run is traceable in the GitHub Actions history with its backup artifact.

## D8 — Platform Extensions & Schema Drift Allowlist

**Decision:** The schema drift check (`scripts/check-schema-drift.sh`, used by
`scripts/db-reset-sync.sh` and both drift steps of `db-remote-sync.yml`) fails on
**any** statement printed by `supabase db diff` that is not listed in
`supabase/drift-allowlist.txt`. The allowlist is versioned and every entry carries
a comment explaining why it is tolerated.

**Extensions:**
- `hypopg` and `index_advisor` exist on the hosted project, so they are declared in
  `20261027000000_declare_platform_extensions.sql` and repo and remote match.
- `pg_net` is **not** installed on the hosted project and must not be. The CLI
  shadow database that `supabase db diff` builds always contains it, so the diff
  always proposes `drop extension if exists "pg_net";`. That single statement is
  the only allowlist entry (decision of 2026-10-27).

**Rules:**
- Drift is never excluded by pattern or by schema; only exact statements in the
  allowlist are tolerated.
- Adding an allowlist entry requires the reason in the file and an update to this
  section.
- `custom_access_token_hook` is enabled locally in `supabase/config.toml`. The
  hosted project's Auth hook configuration lives in the dashboard
  (Authentication → Hooks), is not part of the database, and is untouched by
  `db-remote-sync` resets.

## D9 — Remote Sync and the Access-Token Hook

**Decision:** The hosted project's `custom_access_token_hook` is disabled for the
whole duration of a `db-remote-sync` run and re-enabled only after a run ends green.

**Why:** a reset drops and recreates schema `public`, including the hook function and
the tables it reads. While the hook is enabled and missing or half-migrated, GoTrue
fails every sign-in and token refresh with "Error running hook URI". The hook setting
lives in the dashboard, not in the database, so the reset does not change it.

**Procedure:**
1. Dashboard → Authentication → Hooks → "Customize Access Token (JWT) Claims":
   **disable** the hook (Postgres → `public.custom_access_token_hook`).
2. Run `db-remote-sync` (`mode`, `CONFIRM`, optional `load_seed` / `owner_email`).
   The first and last steps of the workflow print this reminder.
3. Only if the run ends **green**: **re-enable** the hook, pointing at
   `public.custom_access_token_hook`.
4. **Sign out and sign in again.** Existing tokens were issued without the hook and
   carry no `tenant_id`; tenant-scoped policies return nothing until a new token is
   issued.

If the run fails, keep the hook disabled, fix the cause, and run the sync again.

## D10 — ARCO: Suppression (`anonymize_user`)

**Decision:** `anonymize_user(p_user_id, p_arco_request_id)` is the **final,
irreversible suppression step** of an ARCO cancellation, not its first step.

**Behaviour:**
- Requires a tenant admin (RBP v2) and a `cancelacion` request for that user in
  status `pending` or `in_progress`; refuses users already anonymized.
- `users`: name and email replaced by a random `ANON-xxxxxxxx` token (not derived
  from the user), `is_anonymized = true`, `status = TERMINATED`, `deleted_at` set.
- `ec_personal_information`: every personal column is cleared (name replaced by
  the token; date of birth, gender, marital status, nationality, identifiers,
  contact, address, country, emergency contact and event reason set to NULL).
- Personal values already present in the tenant's `audit_logs` (`diff`,
  `details_json`) are replaced with `[suprimido]`; the rows are kept.
- `audit_logs` records only the event: actor (`user_id`), time (`created_at`),
  subject (`entity_id`) and `arco_request_id`. No re-identification map exists.
- Kept: `users.id`, `auth_uid`, `employee_id`, `ec_job_information` (reporting
  line), all other ids and audit rows.

**Pendiente — Fase 10:** bloqueo previo a la supresión según la LFPDPPP 2025 y
plazos de conservación de LFT art. 804, LSS art. 15 y CFF. Validar plazos con
asesoría jurídica antes de operar con clientes reales. Mientras tanto, la
cancelación ARCO no debe ejecutarse en tenants productivos.

## D11 — Manual Project Settings and Privileged RPCs

**Manual settings (hosted project, not in migrations):** some Supabase Auth
settings live in the dashboard and are not reproduced by `db-remote-sync`:
- **Leaked password protection** (HaveIBeenPwned check): Dashboard →
  Authentication → Attack Protection (password security). Enabled manually by
  the project owner when the plan allows it. The `auth_leaked_password_protection`
  advisor stays until it is turned on.
- **Custom access token hook**: see D9.

**Privileged RPCs (SECURITY DEFINER, executable by `authenticated`):**
- `write_audit_log(...)`: ignores the tenant and actor it receives and always
  records `requesting_tenant_id()` and `current_app_user_id()`; fails for callers
  without tenant. `audit_logs` has no INSERT policy or privilege for `anon`,
  `authenticated` or `prisma_app`: entries are written only through this function.
- `insert_effective_record(table, user, data, start)`: only `ec_job_information`,
  `ec_compensation` and `ec_personal_information`; caller must hold app_role
  `owner` or `hr_admin` and the subject must belong to the caller's tenant;
  `tenant_id`, `user_id`, dates, ids and unknown columns are rejected in `data`;
  values are cast through `jsonb_populate_record`.

## Known Risk — Open SELECT on Permission Matrix Tables

**Status:** Accepted (temporary). Registered 2026-10-28.

**Tables affected:** `permission_roles`, `role_permissions`, `permission_groups`,
`role_grants`.

**Current RLS policies:** SELECT is open to every `authenticated` user within their
own tenant (filtered by `requesting_tenant_id()`). INSERT/UPDATE require
`is_tenant_admin()`. DELETE has no policy (soft-delete only).

**Why it exists:** The `can()` authorization function (RBP v2) runs Prisma queries
against `role_permissions` and `role_grants` from the application layer using the
caller's JWT. If SELECT were restricted to admins, non-admin users would lose
authorization resolution — every `can()` call would return `false`.

**Risk:** Any employee can read the full permission matrix of their tenant via the
Supabase client: role names, permission keys, actions, group memberships, and grant
scopes. This is an information disclosure issue — the structure of the RBAC model
is visible to unprivileged users.

**Planned fix (authorization hardening loop):**

1. Move `can()` evaluation to a `SECURITY DEFINER` PostgreSQL function that reads
   the permission tables with elevated privileges (bypassing RLS), receives the
   user ID, permission key, action, and optional target/field parameters, and
   returns a boolean. The application calls `SELECT can(...)` instead of querying
   the tables directly.
2. Restrict SELECT on `permission_roles`, `role_permissions`, `permission_groups`,
   `role_grants`, and `group_members` to `is_tenant_admin()`.
3. Unify `app_role` (JWT claim) with RBP v2 so that admin detection also runs
   through the permission chain instead of relying on a static role string.

## Known Risk — Integration Tests Use Raw SQL Instead of `can()`

**Status:** Accepted (temporary). Registered 2026-10-28.

**Affected tests:** `admin-center-authz.test.ts` — the `canViaRbp()` helper.

**Current state:** The integration tests verify the RBP permission chain
(`group_members` → `role_grants` → `role_permissions`) by querying the database
directly with a raw SQL `EXISTS` check. They do **not** call the application-level
`can()` function from `@/lib/authz/can.ts`.

**Risk:** If `can()` diverges from the raw SQL logic (e.g. adds caching, changes
the join order, introduces field-level or population-based filtering), the tests
will still pass while the real authorization path is broken.

**Planned fix (authorization hardening loop):**

1. Once `can()` is moved to a `SECURITY DEFINER` PostgreSQL function, the
   integration tests should call `SELECT can(...)` directly against the database,
   testing the same code path the application uses.
2. Alternatively, expose a thin HTTP endpoint or Server Action that wraps `can()`
   and have the integration tests call it with each user's token, exercising the
   full stack (JWT → Supabase client → `can()`).

## Known Risk — Admin Center Cannot Create or Edit Roles

**Status:** Accepted (temporary). Registered 2026-10-28.

**Affected component:** `apps/web/src/components/role-manager.tsx` — "Nuevo Rol"
button and role editing UI.

**Current state:** The Admin Center's "Gestionar Roles" page renders an expandable
list of roles, permissions, groups, and grants. The "Nuevo Rol" button opens a
modal, but the modal has no Server Action or API endpoint wired to it — submitting
does nothing. Editing existing roles (rename, add/remove permissions, change group
assignments) is similarly non-functional; the UI is read-only.

**Risk:** Administrators who expect to manage roles through the UI will find it
inoperable. Currently, role and permission changes can only be made via direct
database operations or migrations.

**Planned fix:**

1. Implement Server Actions for role CRUD (`createRole`, `updateRole`,
   `deleteRole`) gated by `admin.manage_roles:edit`.
2. Wire the "Nuevo Rol" modal and inline-edit controls to these actions.
3. Add integration tests that verify CRUD operations respect RBP guards.
